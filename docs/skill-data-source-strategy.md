# Skill：加密/美股/科技新闻数据源策略

> 对应原始任务 Step 1："寻找如何收集全网 crypto、美股、高度相关行业（科技）新闻，
> 梳理数据源接入方案、best practice、权威性评估、效果评估"。
> 本文是这项工作的沉淀，基于本项目实际接入、实测、以及一次严谨的覆盖率交叉验证
> （详见 §5）写成，不是纸面调研。

## 二、逐类接入方案与 Best Practice

### 2.1 RSS 直连（英文头部 + 二线 + 中文 + 宏观）

**Best practice**：
- `feedparser` 解析，`published_parsed`/`updated_parsed` 取真实时间，**不要用抓取时间代替**——这是时效因子 T 的输入，用错会让所有内容看起来一样新
- 单源取数上限要跟着 cron 周期走：4 小时一轮时 30 条够用，改成 12 小时后必须提到 100（本项目踩过这个坑，见 §4）
- **RSS 深度是服务端固定的**，不受你请求参数控制（吴说、BlockBeats 这类高频源实测约 30-50 条）。抓取间隔必须小于"服务端窗口时长 ÷ 发布频率"，否则会滚屏丢失——这是本项目从 4h 改 12h 后暴露的真实 bug（Triple-A 被盗事件排查实锤，详见 `docs/PROJECT_PLAN.md` 已知风险章节）
- User-Agent 要伪装成正常浏览器，否则部分源直接 403

**权威性评估基准**（用于 LLM prompt 里的 `score_authority` 锚点）：
```
1.0  官方公告（交易所公告、监管机构官网）
0.75-0.89  头部媒体（CoinDesk/TheBlock/吴说/BlockBeats）
0.50-0.74  中等媒体（二线英文站、聚合号）
0.30-0.49  聚合/搜索来源
≤0.30  匿名/无法验证来源
```

### 2.2 自建 RSSHub

部分中文源没有官方 RSS（金色财经、Followin、币安公告），自建 RSSHub Docker 容器
（`localhost:1200`）代理生成。**Best practice**：容器要配 systemd 自启，因为它是
单点依赖——挂了会让这几个源全部抓取失败且不易察觉（错误只是 `HTTP 500`，容易被
忽略）。

### 2.3 HTML 解析

无 RSS 的源（ChainCatcher、PANews）直接解析页面。**Best practice**：
- 优先找页面里的 SSR 数据（Nuxt/Next 的 `__NUXT__`/`__NEXT_DATA__` 内联 JSON），
  比正则抠 HTML 稳定得多，页面改版时更容易适配
- 标题里混进的噪音（时间戳、"微信扫码"提示）要用正则清理，见 `crawler/main.py`
  的 `_parse_chaincatcher`

### 2.4 X（推特）—— 用户明确要求的成本敏感区

**用户原始要求**："X 的 API 我后面会购买，但需要节省用量的用法（搜索+RSS+API
结合，API 只查询高相关的材料，而不是乱爬）"

**当前实现（两条腿）**：
1. **KOL 时间线**（`GET /2/users/:id/tweets`）：32 个精选账号，深度召回，
   192 请求/天
2. **全网关键词搜索**（`GET /2/tweets/search/recent`）：450 请求/15分钟额度，
   22 组两段式查询（"同义词组 AND 限定词组"），封顶 200 条/轮送入 LLM

**关于"只查高相关材料"的待改进方向**：当前 22 组查询是**预设关键词**，本质仍是
广撒网（虽然比裸查询精准）。更贴近用户要求的做法是**先用零成本渠道
（RSS/Google News）确定当轮的热点实体，再用 X API 定向查询这些已知实体**——
把 API 配额集中花在"已经确认有新闻价值"的话题上。这是记录在
`docs/PROJECT_PLAN.md` 待办里的重构方向，需要等用户实际购买 API 后按真实额度
设计。

**成本教训（实测踩过）**：X 搜索一度产出 528 条/轮，全部送 LLM 结构化，让单轮
成本从 $3.65 涨到 $9+（2.5倍）。**真正的成本敏感点不是 X API 本身（Basic 层
固定月费，不按次计费），而是召回量对下游 LLM 结构化成本的放大**。已加
`MAX_ITEMS_PER_RUN=200` 硬顶，按互动量排序保留最有价值的部分。

**质量过滤经验**：全网搜索比 KOL 时间线多两类特有噪音——
- **微额"鲸鱼"机器人**：机械发布"whale just bought $1.6K of $TICKER at $2.3M MC"
  模板，格式像鲸鱼追踪但金额毫无意义
- **单项目内容农场**：一个账号批量发同一项目的模板化"深度分析"软文，每条话术
  不同、不触发关键词过滤，但重复推销本身就是特征

  应对：不要试图穷举关键词模式，用**账号层面的结构性限制**（单账号单轮最多 N 条）
  更通用、更难绕过。

### 2.5 搜索引擎（Google News + ddgs）

**用户原始要求**："google 一搜就能搜出来的 news 我们也得有"

**关键坑（务必记住）**：Google News RSS **默认按相关性排序**，裸查询返回的
结果中位年龄可达 37-130+ 天。**必须加 `when:Nh`/`when:Nd` 时间算子**才会返回
真正新鲜的内容，且中位年龄随算子单调变化（`when:1h`→0.8h，`when:6h`→3h，
`when:1d`→7-19h）。这个坑如果不知道，会以为"Google News 召回质量很差"，
实际上是没加对算子。

**Bing News RSS 实测不可用**：中文查询全部返回 0 条，英文的时间过滤参数
形同虚设。**不建议为它单独维护解析逻辑。**

**ddgs 的 `.news()` 接口**可作英文补充（不是主力），中文查询 100% 失败
（`DDGSException: No results found`），只对英文查询启用。

### 2.6 行情信号（不是新闻源，是事件生成器）

**为什么需要它**：覆盖率交叉验证证明新闻覆盖率其实有 91.9%（后来更严谨的方法
测出真实数字是 29.9%，见 §5），但**行情异动类事件只占库里 3.9%**。原因很简单：
没有媒体会把"BTC 24h 跌 5%"写成新闻。这类信号必须从行情 API 直接生成事件，
不能靠加新闻源解决。

**技术难点**：币安官方 API（`api.binance.com`）在美国 IP（本项目 VM 所在地）
返回 **451 地域封锁**。解决方案：现货数据走 `data-api.binance.vision`
（同数据，未被封锁的 CDN 域名），合约数据（资金费率/持仓量/爆仓）走 OKX 公开
接口为主、Hyperliquid 兜底。

**成本**：纯规则计算（涨跌幅/突破关键价位/成交量放大倍数），零 LLM 调用。

### 2.7 CoinMarketCal（催化剂日历）

未来 14 天的代币解锁/主网上线/硬分叉/会议等**已知日程**。免费层 3000 请求/月，
每轮 1 次调用足够。**注意**：这类内容的"发布时间"应该用抓取时间而非 API 返回的
`createdAt`（那是日历条目被录入的时间，可能是几个月前），否则会被新鲜度过滤
误杀。

## 三、权威性评估方法论

不看粉丝数/流量，看**信息独立性 + 事实可验证性**。分层锚点：

| 层级 | 标准 | 示例 |
|---|---|---|
| 官方一手 | 监管机构官网/官推、交易所公告 | sec.gov、Binance Announcement |
| 头部媒体 | 独立采编、有更正机制 | Bloomberg、CoinDesk、吴说 |
| 中等媒体 | 二线独立站点 | AMBCrypto、BeInCrypto |
| 聚合/转载 | 无一手信息，编译他人报道 | 部分搜索引擎命中 |
| 陌生个人账号 | 无法验证身份和历史记录 | X 全网搜索的非白名单账号 |

**多源交叉验证**是比信源分层更强的客观信号——但"独立"的定义要按**机构**而非
**feed** 计算：`BlockBeats快讯`、`BlockBeats文章`、`X/BlockBeatsAsia` 是同一家
机构的三个出口，只能算 1 个独立信源。这是 `crawler/verification.py` 的核心
设计（详见该文件的机构别名表）。

## 四、抓取频率与召回稳定性的权衡

**这是本项目一个重要的实践教训，值得写进 best practice**：

抓取频率不是越低越省钱越好。cron 从 4 小时改成 12 小时降本后，排查漏召发现
高频源（RSS 服务端窗口固定约 30-50 条）会把发布密集期的内容挤出窗口，**永久
错过**（不是我们的新鲜度过滤或去重误杀，两者实测误杀率均为 0）。

**正确的解法是解耦"抓取频率"与"处理频率"**：抓取本身几乎不花钱（RSS/HTML/
搜索引擎都是带宽成本），真正的成本大头是下游 LLM 结构化。所以：
- 免费源用独立的高频 cron（本项目取 2 小时）只做「抓取 + 存档」，不进 LLM
- LLM 处理仍按现有低频节奏（本项目 12 小时）批量消费存档内容

这样高频源不再受处理周期限制而滚屏丢失，但 LLM 调用次数和频率完全不变，
成本不变。实现见 `crawler/staging.py`。

**X 是例外**：按用户明确要求，"除了 X 这种要 API 额度的接口，其它都可以更高频
拉取"——X 维持原节奏，不接入高频存档路径。

## 五、效果评估方法论（覆盖率交叉验证）

### 5.1 不要用简单方法评估覆盖率

本项目第一次评估用"关键词重合"做匹配，得出 91.9% 的覆盖率——**这个数字被
严重高估**，原因：
1. 关键词重合会把"同主题不同事件"算成命中（不够精确）
2. 当时库里有大量重复行，让任意对照条目都更容易撞上某一行

第二次用更严谨的方法重测（更大样本、公平时间窗口、多种匹配口径交叉验证），
真实覆盖率是 **29.9%**（事件级）。这个数字差了 3 倍，说明评估方法本身要经得起
质疑。

### 5.2 语义相似度（cosine）不能单独作为匹配主口径

实测 cosine≥0.75 的精确率 93.3% 但**召回率只有 47.2%**——跨媒体改写的同一
事件大量落在 0.60-0.75 区间（如 "Bitcoin plunges below $60,000" vs "BTC drops
under $60k" 只有 0.775）。纯 cosine 会系统性低估覆盖率约一倍。

**正确做法**：cosine 做候选召回（拉 top-N 相似的做候选），最终判定交给 LLM
逐条判断"是否同一真实事件"，而不是卡死一个阈值数字。

### 5.3 分层看覆盖率比总体数字有用得多

按"有几家独立媒体报道"分层是本项目做过的最有决策价值的一刀：

| 报道媒体数 | 覆盖率 |
|---|---|
| 3 家及以上 | 100%，一条没漏 |
| 2 家 | 77.8% |
| 仅 1 家 | 22.0% |

**结论**：系统没有漏掉任何一条被 3 家以上独立媒体共同报道的新闻，问题集中在
"信源盘子太小、长尾密度不够"，而不是"错过大事"。这个结论直接决定了后续该
优先扩信源还是优先调阈值。

### 5.4 漏召要做归因，不能止步于"漏了多少"

对每条漏掉的内容分类：信源根本没接 vs 抓到了但被过滤器误杀 vs 抓到了但没
落成独立事件。本项目实测新鲜度过滤和粗去重误杀率均为 0——意味着"扩信源"
比"调过滤阈值"性价比高得多。这个归因过程本身比覆盖率数字更有指导价值。

## 六、Cheat Sheet（10 条）

1. RSS 时间戳用真实发布时间，不用抓取时间——影响时效因子
2. 高频源的服务端窗口是固定的，抓取间隔必须小于"窗口 ÷ 发布频率"
3. Google News 必须加 `when:` 算子，否则捞回几十天前的旧闻
4. X 搜索的成本敏感点是下游 LLM 结构化，不是 X API 本身
5. 全网搜索的质量过滤要防两类特有噪音：微额鲸鱼机器人、单账号内容农场
6. 币安主站 API 在部分云厂商 IP 段会被地域封锁，需要 CDN 域名或备用交易所兜底
7. "多源交叉验证"要按机构去重，不是按 feed 去重
8. 抓取频率和 LLM 处理频率应该解耦：免费源可以高频抓取存档，处理仍按预算节奏
9. 评估召回覆盖率要用 LLM 逐条判定做主口径，纯关键词/纯 cosine 都会系统性偏差
10. 漏召分析要做归因，不要止步于百分比数字——归因结果才是行动指南
