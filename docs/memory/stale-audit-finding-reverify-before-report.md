2026-07-31 B9 全系统检修的一个 P0 发现："两条备份 cron（周日11:00/每日03:30）
从未产出过任何文件"——审计 agent 跑的那一刻，这句话是真的（backups/ 目录下
确实没有 daily_*/weekly_* 文件，syslog 里零 mysqldump 执行记录）。写报告过程
中没有直接把这句话原样抄进最终交付物，而是重新查了一次，发现**当日 03:30
那一轮在我核实的过程中真实触发成功**——cron 日志 `CRON[267526]` 可查，
`daily_20260731.sql.gz` 37MB 真实存在。审计的结论和我重新核实的结论都是
"当时真实"的，但直接采信旧结论会把已经解决的问题继续当活跃故障汇报给老板，
造成误判。

**Why**：审计/发现类结论本质是一次性快照，尤其是"从未 X 过"这种绝对陈述——
它对"审计跑的那个时间点"成立，但系统状态可能在写报告的几十分钟到几小时内
就发生变化（这次恰好是 cron 定时任务的下一个触发窗口正好落在核实过程中）。
如果报告撰写到交付之间有实质性时间差，且陈述本身是"可现场核实"的类型
（不是"过去发生过某事"这种事后无法改变的历史事实），继续直接引用旧结论
就是在向用户汇报一个可能已经不准确的状态。

**How to apply**：
1. 撰写正式报告/汇报材料前，扫一遍待引用的"发现"里有没有"从未/一直/所有/
   零"这类绝对量词的陈述，尤其是涉及"某个自动化机制是否真的在运行"的——
   这类陈述过期风险最高，且过期后果最严重（要么错误地制造恐慌，要么错误
   地掩盖真实问题）。
2. 能现场重新核实的，花几分钟重新查一次，不要图省事直接照抄。
3. 如果重新核实后结论变了，**两个结论都要写进报告**，各自标注观测时间点，
   而不是只留最新结论（旧结论消失会让人以为问题一直没发生过，掩盖了它
   确实发生过、只是被后续事件覆盖的事实）；同时指出更深层的、不因这次
   好转而消失的问题（这次是"同机同盘无异地副本""静默失败无告警""零恢复
   演练"三条依然成立）——避免因为一次好转就整体判定"没事了"。
