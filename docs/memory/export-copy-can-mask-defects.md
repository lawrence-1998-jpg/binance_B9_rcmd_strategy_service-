2026-08-02 B9 流程图重排。为了肉眼检查，我把页面里的 SVG 导出成独立文件
（把 `var(--xxx)` 换成实际色值），渲染出来看着完全正常。

但 SVG 里有个 `class="lbl"` 的文字，**页面 CSS 里只有 `.note .lbl` 这类后代
选择器，裸用的 `.lbl` 从来没命中过任何规则**——线上它一直以纯黑 14.5px 默认字
渲染，跟全图排版语言完全不搭。存量问题，之前就在那儿。

**我没发现，恰恰是因为我的导出脚本为了让 SVG 自包含，顺手补了一条 `.lbl` 定义。**
导出图是对的，线上是错的。我验收的是我自己修补过的那一版。

**Why 这类坑通用**：任何"导出 / 打包 / 内联 / 快照"步骤都在**补全依赖**——
内联 CSS 变量、内联字体、内联 JS、把相对路径改绝对。而线上出问题的方式，
恰好经常就是**某个依赖没接上**。补全动作与故障模式是同一个维度，导出件天然
对这类故障免疫，于是它成了一面照不出问题的镜子。

**How to apply**：
1. **在真实运行环境上跑断言**，别在导出副本上跑。这次改成在线上页面跑
   `getComputedStyle`，问题一秒暴露。
2. 断言要覆盖"**依赖有没有接上**"，不只是"位置对不对"。这次新加两条，正是
   它们抓到的：
   - 每个 text 必须命中样式表里**已定义**的类（`!classList.some(x=>known.has(x))`）
   - 没有 `fill: rgb(0,0,0)` 的文字（纯黑=退到了默认值的信号）
   同类可迁移断言：没有默认字号、没有 fallback 字体、没有 404 资源。
3. 导出件只用来**给人看**，不用来**做验收结论**。要么别在导出脚本里补依赖，
   要么补了就必须另外在真环境验一遍。
4. 顺带：验完还要确认"我看的那张图 == 线上那张图"。这次是把线上 HTML 拉回来
   抽出 SVG 与本地源码逐字节 diff（24941 == 24941）。
