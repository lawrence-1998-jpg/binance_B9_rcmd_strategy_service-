**报出任何数字之前，先问一句：我测的这个量，和我要声称的那件事，是同一件事吗？**
中间只要隔着一层没测的转换，结论就可能完全相反。

**Why**：2026-07-29 我给 Lawrence 报了一个**完全错误的成果**。当时刚把
`storage.load_enrich_cache` 的 prompt_hash 门禁放开，我跑了个验证脚本，输出
"400 条待处理里命中缓存 400 条（100%）… 净赚 400 条免费复用，约省 \$17.60"，
并把这个数字当作改动生效的证据报给了用户。

实际上**真正能用的是 0 条**。我测的是"SQL 能不能按 url_hash 取到行"，而我声称的
是"这些缓存能不能被 pipeline 直接使用"——中间隔着一层 `_valid_cached_enrichment`
字段校验。那批缓存是加 `market_scope` 必填字段之前算的，SQL 全命中、字段校验
一条不过，pipeline 照样全额回落到付费的 OpenAI 直连账号。是我自己在下一步排查
时才发现的（`llm_cache_hits: 0` 与我的"100% 命中"直接矛盾）。

同一个盲区当时还差点造成第二个更严重的后果：我顺手把**派活侧**
（`enrich_bridge` 的 `/api/enrich/pending`）也改成不认 prompt_hash，逻辑上"有
缓存就不再派活"。结合上面的字段校验失败，会导致这些条目**永远不会被重新计算、
也永远不能被使用**，系统锁死在付费回退且没有任何自愈路径。

**How to apply**：
- 验证脚本要**测端到端的那个结论**，不是测中间某一步。想证明"缓存能省钱"，
  就该跑一次真实 pipeline 看 `llm_cache_hits`，而不是数 SQL 返回了多少行。
- 报喜之前主动找一个能证伪的角度。这次只要多问一句"那为什么日志里
  `llm_cache_hits` 是 0"，当场就能发现。
- 数字带上口径。"400 条 SQL 命中"和"400 条可用"是两句话，不能省成一句。
- 改**成对的逻辑**（读侧/写侧、派活侧/复用侧、生产者/消费者）时，先分别想清楚
  两边各自要回答什么问题。这次两边的正确答案本来就**不对称**：复用侧问"我现在
  能不能用"（任何有效缓存都行），派活侧问"还有什么要按当前口径算"（必须认当前
  版本）。把它们"统一"掉才是 bug。
