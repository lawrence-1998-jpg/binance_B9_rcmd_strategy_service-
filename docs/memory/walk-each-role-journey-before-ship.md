2026-08-06 B9 原子能力审批功能。上线时我验了 13 项：权限边界、状态机、幂等、
拒绝必填原因、fail-open、表单三态互斥……全绿。用户提交第一条真实申请后一句话打回：

> 得能让我查看这个申请的具体内容。好好设计一下，不要再犯这种基础功能走不通的错误了。

列表只渲染了标题+状态；`/detail` 接口在后端躺着，前端没接。**审批人要在看不到
申请内容的情况下决定批还是拒**——整个功能的第一步就是断的。

**Why 机制级测试挡不住它**：我测的每一项都是"某个端点/某段逻辑对不对"，
没有一项在问"**某个角色能不能从头到尾完成他的事**"。旅程断口不表现为任何
断言失败——所有接口都正常，只是没人把它们连成用户要走的那条路。

**How to apply（交付前的角色旅程清单）**：
1. **列出这个功能的全部角色**（本例：申请人、审批人、旁观同事），逐个走完整旅程：
   - 申请人：填表 → 提交 → 在列表里认出自己的单子 → 看到审批结果和原因
   - 审批人：发现有待办 → **读到申请的完整内容** → 决定 → 看到结果生效
   - 旁观者：看到所有单子的状态与拒绝原因
2. 走的时候只准用**屏幕上有的东西**。哪一步需要"去查库/调接口才知道"，哪一步就是断的。
3. 每类表单/每种状态各真实提交一条走完，别只测一类推及其它。
4. 与 [[definition-of-done-user-surface]] 的区别：那条说"要在用户界面上验证"，
   这条更进一步——**按角色分别验证**，因为不同角色看到的是同一界面的不同切面，
   我这次恰恰是站在"提交者+管理员合体"的视角测的，审批人独有的那一步（读内容）被跳过了。

顺带两条实现层教训（同一次修复中）：
- 事件委托的点击目标常是子元素，必须 `closest('[data-x]')` 往上找；直接比对
  `e.target` 会"点标题没反应、点空白才有反应"——又一种基础走不通。
- 详情深链（`?cap=N`）不是锦上添花：通知里给直达链接、headless 截图验证展开态，
  都靠它。可展开的东西尽量做成可深链的。
