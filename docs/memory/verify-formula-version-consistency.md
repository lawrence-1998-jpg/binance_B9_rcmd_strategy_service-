只要改了写进库的**打分公式或权重**，上线前必须做一次全库反算比对：按当前
公式重算一遍，看有多少行的存量分对得上。对不上的部分要么重算，要么在结论里
明确排除。

**Why:** 2026-07-29 在 B9 加完广度/冲击力两个因子后，顺手查了一下——3174 行
里只有 **402 行（13%）**的 `importance_score` 是按现行七因子公式算的，
1865 行还是旧五因子，907 行是中间版本。前端按这个字段排序，等于把三个不同
公式算出来的分放在同一个列表里比大小。

**致命的地方在于它会污染效果测试**：如果不先修，"排序改好了吗"测出来的差异
有很大一部分只是"哪些行碰巧被新公式重算过"，结论完全没有意义——而且看起来
是有效果的，很容易就这么报上去了。

**How to apply:**
- 重算脚本按阶段拆：需要 LLM 的语义字段单独一阶段（唯一花钱的），纯计算的
  离线重算，最后合成总分。分阶段才能幂等、可中断重跑。
- **不要重算依赖"当前时刻"的因子**（时效、热度）。离线重算会把所有历史条目
  刷成"很旧"，制造出本次改动之外的新变化，让前后对照失去意义。
- 重算**之前**先 `CREATE TABLE snapshot AS SELECT` 存一份旧排序——这既是回滚
  依据，也是效果测试唯一干净的对照组（事后模拟旧公式模拟不出混版本的真实状态）。
- 同时查一下 UPSERT 的 `ON DUPLICATE KEY UPDATE` 有没有漏刷新新增的分数列——
  漏刷会让老行永远停在 NULL，然后被兜底默认值静默按最低档计。
- **把这件事沉淀成永久机制，不要只当一次性修复**：加一列 `scoring_version`
  标记"这行是哪个版本算的"，改公式必须同步 +1；QA 门禁常驻两条断言（版本号
  落后 = 0、抽样核对版本号与实际数值真的吻合），不要写个一次性脚本跑完就扔。

**追加教训（同一天真实发生）：** 上面这套护栏部署几分钟后，当天最新一轮
生产 pipeline 一跑完，QA 的"版本号与数值吻合"断言就抓到 121 行不吻合——
不是历史遗留，是**这次改造自己顺手引入的新问题**（把某个分数列的 UPSERT
从"每次刷新"改成"COALESCE 只填空"，但依赖它的总分列还是"每次刷新用最新值"，
两者立刻对不上）。说明这类 bug 不是"这次改完就没事了"，是会随便一次后续改动
就重新出现的持续性风险——护栏必须常驻在 QA 门禁里、覆盖"新代码上线后的第一次
真实写入"，不能只在改造当天手动跑一次就算完事。
