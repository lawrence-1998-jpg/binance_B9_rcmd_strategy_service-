搜索聚合器（Google News RSS、ddgs 等）返回的 `published_at` 是**它重新分发
这条内容的时间**，不是原文发布时间，两者可以差任意久。而且这类条目的
summary 通常只是**标题复读 + 来源名**，没有一个字的正文。

**Why:** 2026-07-29 在 B9 出的事故：一条 6/27 的旧闻以 A 档、日期 07-28 在
前端展示，差整整一个月。之前专门为"信源时间戳骗人"建过一道"LLM 从正文提取
真实事件日期"的兜底闸——但它需要正文，而聚合器恰恰不给正文（实测 2870 条
web_search 里 2640 条即 92% 无正文，平均摘要 90 字符 vs 直连 RSS 的 193）。
LLM 无从提取，event_date 只能回落成那个假时间戳，闸对着假日期做校验、必然
放行。**防线建错了层**，不是阈值没调好。

同一批还抓到第二种失败模式：S 档"韩股据报暴跌33%"（实际当天 KOSPI 跌
10.84%，33% 是把月累计跌幅当成单日崩盘）——同样是只有标题没正文，模型把
有歧义的数字读错。所以聚合器无正文条目不只是"时间不可信"，是"整条内容的
理解都建立在一个标题上"。

**How to apply:**
- **把"媒体权威度"和"时间可信度"分开**——正规媒体（财联社/CNBC）经聚合器
  分发之后，时间戳已经不是它自己声明的那个了，不能因为发行方权威就信时间。
  混为一谈正是这次事故能发生的认知原因。
- 判定用「来源是聚合器 **且** 摘要去掉标题后残留 < 25 字符」，放在 LLM
  **之前**丢弃：纯字符串操作不需要模型，早丢早省钱。
- **判定必须是"全部信源都是聚合器"而不是"任一"**：同一篇文章常被直连 RSS
  和聚合器各收一次，直连那份带可信时间戳，是要保留的。
- SQL 里查 JSON 数组的 type 字段必须限定路径 `'$[*].type'`——不限定的话
  Google News 的 url 里带 `/rss/articles/`，会被误匹配成 rss 类型。
- 删聚合器孤证前先验证"自纠正"：重要新闻会被可信信源冗余覆盖。实测那条
  造假的"韩股33%"旁边就躺着 91 个信源的准确版本，删孤证不丢真新闻。
