2026-07-30 给 Benzinga 回填 4 天历史（3454条）当天连踩三个坑，用户当场抓到
（"怎么都只有benzinga的内容了，而且都是28号的旧新闻"），且再下午就是老板演示。

**坑1 · "最近N条"语义污染**：实验室取数是 `ORDER BY 入库时间 DESC LIMIT 300`。
稳态下入库顺序≈发生顺序，回填瞬间打破——300/300 全变成单一信源的旧闻。
**坑2 · 同优先级 FIFO 饿死新数据**：回填条目继承了信源的高优先级（P0），
与当天新抓的头部媒体同级排队，且 fetched_at 更早 → 新闻被 1859 条旧闻堵住，
按每小时400条要4-5小时才轮到。
**坑3 · 成本旁路**：手动催 pipeline 消费，预处理桥（免费路径）没来得及缓存，
800 条直接走个人付费账号（$7.12）。

**Why**: 回填改变的不是数据总量，是三个隐含假设——"新入库≈新发生"、
"同优先级内先到先处理是公平的"、"消费速度不会超过缓存速度"。

**How to apply**: 任何批量回填前过三关——①检查所有"最近N条"类查询是否
按事件时间而非入库时间；②回填条目显式降优先级（或加"backfill"标记），
别让它和实时数据同队；③先让免费预处理跑在前面，忍住不手动催消费。
出问题的修复顺序：先降级存量解队（UPDATE priority，秒级止血），再修取数轴。
相关：[[verify-recall-by-url-not-keyword]]、[[b9-enrich-bridge]]

**2026-08-04 实证（停摆 3 天、积压 1.1 万条）**：第二个坑"同优先级 FIFO 饿死新数据"
真的发生了，而且比预想的更隐蔽——队列确实在稳步追平，**但产品仍然是坏的**：
先啃两天前的稿子，首屏全是旧闻，而"大盘情绪"取的是 24h 窗口，一直算不出来。
`积压在下降` 这个指标全程绿灯，掩盖了 `用户看到的还是三天前`。
修法：同优先级内改成**新的先做**（`fetched_at DESC`）。新闻价值随时间衰减，
排队久不该换来优先权。注意**派活侧与消费侧两处 ORDER BY 必须逐字一致**，
错位会让缓存命中率静默归零（现象是"worker 在跑、事件不涨"）。
