**缺失的数据只能是"缺失"，不能被替换成一个貌似合理的默认值。** 尤其是时间戳、
来源、权威度这类**下游会当成事实来用**的字段。

**Why**：2026-07-29 出的真事故。`crawler/main.py` 的 `normalize_published_at`
里有一行 `if not value: return now.isoformat()`——"拿不到发布时间就当成现在"，
当时的注释理由是"多数 HTML 抓取源本就没有可靠时间戳"，看起来是合理的工程妥协。
配合 `fetch_binance_square()` 走 ddgs 搜索、**结构性拿不到日期**（代码里写死
`published_at=""`），结果是：一条 **2024-08-21** 的币安广场帖（DOGS 第 57 期
Launchpool）被盖上"现在"的时间戳，以 `date=2026-07-26` 的身份进入事件库，
在前端和当天新闻并排展示。Lawrence 的原话："被发现一条我的 reputation 就毁了。"

关键点是：**这类 bug 靠日期过滤器永远拦不住，因为数据本身在说谎**。上游任何
"缺失→默认值"的替换，都会让下游所有基于该字段的校验失效。

**How to apply**：
- 写兜底逻辑时先问一句："这个默认值会被下游当成事实吗？"会 → 不能填，要么
  丢弃该条，要么显式标记为 unknown 并让下游能识别。
- 特别警惕 `or`/`if not x` 这种简洁写法把空值悄悄变成有值。
- 数据源接入时先确认它**能不能提供**关键字段。拿不到发布时间的渠道（搜索引擎
  结果尤其典型）不能进时效敏感的产品，这不是调参能修的，换取数方式才行。
- 连带教训：**QA 门禁要有内容正确性不变量，不只有接口形状**。事故发生前我刚
  报过"QA 98/98 全绿、达到交付标准"，但那 98 条全是"接口通不通/鉴权拦没拦住/
  字段在不在"，**没有一条验"展示出去的内容是不是真的"**。修复后补了三条红线：
  默认只返回 7 天内、库内不得有事件日期早于采集 7 天的行、库内不得有无发布
  时间来源的条目。
