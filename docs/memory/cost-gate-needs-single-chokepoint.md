2026-08-02 B9 做"关掉个人 API key 就一分钱不花"的开关。动手前盘点发现：全项目
9 个实际付费调用点、4 处各自独立的 `OpenAI(**kwargs)` 构造，没有统一入口。
**在那种结构下"加一个总开关"这件事根本做不到**——总会漏掉一处，而漏掉的那处
不会报错，只会在月底账单上出现。所以第一步不是加开关，是先建单一闸口
（`crawler/llm_gate.py`），9 个付费点全部改走它。

**Why / 三条必须守住的设计原则**：

1. **Fail-closed**：DB 连不上、表不存在、值解析失败——一律当"关闭"处理。
   一个"因为读不到配置就放行"的闸口不叫闸口。同理日配额计数查不到时按
   "已用满"处理：高估的后果是提前停手，低估的后果是超预算。
2. **开启必须带自动失效**：紧急开关最大的失败模式不是"开不了"，是"忘了关"。
   把它从流程纪律变成机制保证（默认 6h 到点自动回落），再叠一道日配额兜底
   （自动失效管"忘记关"，配额管"开着的这几小时里量突然暴涨"，方向不同）。
3. **"允许花钱"≠"有钱可花"**：开关打开但 key 没配/被吊销时，SDK 是**抛异常**
   而不是返回 None。不包住的话，一条没配好的 key 会炸掉整批任务。两种情况
   对调用方处理方式相同（拿不到就留给下一轮），但必须都不崩。

**最危险的那个坑（差点造成永久数据丢失）**：闸口跳过条目后，下游的
"标记已消费"逻辑照旧把**本轮取出的全部条目**标记掉了——被跳过的从此再也
不会被任何一方领取。而且是静默的，日志只说 "marked N items"。
更微妙的是修的时候第一版还修反了：用"成功处理的 id 集合"做正向筛选，结果
把"被信任闸/去重故意丢弃"的条目也留在了队列里，队列无限增长、每轮重复处理。

**正确口径**：只把**被成本闸拦下**的排除在消费标记之外。"没被处理"有两种
截然不同的原因——推迟（该重试）vs 故意丢弃（已判定不要，重放只会再花一次
同样的钱得到同样的结果），下游记账必须分开，混为一谈时不是丢数据就是
队列爆炸，两个方向都错。

**How to apply**：
1. 做任何"总开关/限流/预算"类需求，先 grep 出全部付费入口数一数。散落多处
   就先收敛闸口，别急着加开关。
2. 闸口默认 fail-closed，异常路径全部走"拒绝"。
3. 排队系统里加"跳过"语义时，务必检查下游的"已处理"标记是按什么口径打的，
   并且**跑一轮真实数据看日志**——这个 bug 靠读代码没发现，是端到端跑完
   看到 "marked 4 items consumed" 那一行才意识到的。
