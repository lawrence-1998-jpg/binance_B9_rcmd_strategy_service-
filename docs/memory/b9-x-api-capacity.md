**2026-07-26 彻底更正**（本条旧版写"450 req/15min 额度闲置、免费已有、优先用
search/recent"——那是请求数视角，完全错误，且正是这个误判导致了烧钱事故）：

Lawrence 的 X API 是**按返回的推文条数计费**，实测 ≈$0.0021/条（单日 $14.88 ÷
约 7000 条）。在错误认知下配置的广撒网（每轮拉 3400 条只留 200 条，6% 产出率）
两天烧穿 credit，余额 -$0.11，全部 X 接口 402 停摆半天。他补了 $10 并要求
"省着用，不影响效果的时候少用一点"。

现行控制（`crawler/x_search.py`，2026-07-26 傍晚 Lawrence 表态"倒也不用这么省"
后从省钱档调到平衡档）：
- 主闸门是**条数预算** `X_SEARCH_POST_BUDGET = 1500`/轮上限，实际约 1200 条/轮
  （≈$2.6/轮、全部 X 成本约 $6/天、$180/月）
- **按类别分级取数**：market/macro 25 条/页（历史上 94% 浪费集中在这两类），
  其余类别 75 条/页；每查询单页
- 21 组查询全部保留（用户明确要求覆盖面不能砍："一搜能出来的新闻要 cover"），
  预算跑不完全部查询时按天轮转起点，保证跨天覆盖所有类别
- 日志看真实花费：`X search: N posts billed (~$X.XX)`

**How to apply**: 任何 X 相关的量调整先换算成"条数 × $0.0021"再动手；召回不够
时只调大 X_SEARCH_POST_BUDGET 这一个数，别动页数/单页条数组合。X 官方 MCP
（api.x.com/mcp）是同一 API 的桥接层、同一份按条计费，接进来不省钱，已评估不接。
