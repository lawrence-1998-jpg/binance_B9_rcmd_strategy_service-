## 第一章 · 开工即建的工程设施

这一章的六件事全部满足两个条件：**开工第一天建，成本不到半天**；**事后补建，成本是若干次生产事故**。B9 项目每一件都是先出事、再补建的，你没必要重走一遍。

每节结构固定：是什么 → 为什么（真实事故）→ 最小落地步骤 → 通用/专属标注。标 [CC] 的是 Claude Code 专属机制，用其它 AI（Cursor/Copilot/其它 agent）时看对应的通用做法。

### 1.1 QA 门禁：把"交付"定义成一个脚本的退出码

**是什么**：一个断言脚本（如 `scripts/qa_gate.py`），跑完输出报告。规矩只有一句：**AI 必须拿到 no bug 报告才允许说"做完了"**。"我觉得改好了"不是交付，脚本绿了才是。

**为什么**：B9 出过两类事故。其一，改了排序公式后，库里 87% 的分数仍是废弃旧公式算的，且从任何界面都看不出来——所有基于它做的效果测试全是假的。其二，AI 把"SQL 查到 400 行"汇报成"缓存可用 400 条"，实际可用 0 条。共性是：**没有机器裁判时，AI 的自我汇报会系统性偏乐观**。

**断言分四层**（按 B9 实测有效的分法）：

| 层 | 断言内容 | 例子 |
|---|---|---|
| 鉴权 | 每个 API 端点带错误 token 必须 401 | 曾因多处鉴权表只改了一处，两次 401 事故 |
| 数据红线 | 业务上"绝不允许"的状态数量必须为 0 | 无日期记录数=0；未来时间戳=0；孤儿外键=0 |
| 公式一致性 | 存量派生值的版本号必须全部等于当前版本 | 见 1.4 |
| 环境同步 | 生产与实验工具取同一份配置、同一条取数路径 | 规则：实验工具禁止私带公式副本——这类漂移在界面上不可见（参见 1.4 的 87% 旧公式事故） |

**最小落地**：
1. 第一天就建 `scripts/qa_gate.py`，哪怕只有 3 条断言。断言失败 `exit 1`，全过打印 `NO BUG REPORT — {日期} — {断言数} passed`。
2. 每次交付前把这段话发给 AI（可直接复制）：

```
交付前必须执行 python scripts/qa_gate.py 并把完整输出贴给我。
只有输出包含 "NO BUG REPORT" 才能宣布完成。
任何断言失败：先修复，再重跑，不允许跳过或注释掉断言。
本次改动如果引入了新的"绝不允许"状态，先加对应断言再写代码。
```

3. 每次事故复盘后加一条断言。B9 两个月积累到 120 条，全部是事故换来的。

**补充红线**：QA 全绿 ≠ 没问题。B9 曾一天被人眼抓出三个 QA 没拦住的问题。交付前追加两个动作：肉眼扫一遍首屏；把报告里的可疑数字在界面上搜一遍。凡是用户一眼/一搜就能发现的问题，就是 AI 的交付底线。

[CC] 把"必须拿到 no bug 报告才算交付"写进项目 `CLAUDE.md`，Claude Code 每轮会自动加载；也可配置 Stop hook 在每轮结束自动跑门禁。**通用做法**：规矩写进 Cursor 的 `.cursorrules` / 其它 agent 的系统指令；自动执行则把门禁挂进 git pre-commit 钩子或 CI 流水线的必跑步骤，效果等价——关键是规矩进入每轮上下文、门禁由机器强制执行，而不是靠 AI 记得。

### 1.2 双档案制：WORKLOG.md + REQUIREMENTS_LOG.md

**是什么**：两个纯 markdown 文件。`REQUIREMENTS_LOG.md` 记**用户原话**，逐轮、倒序、不改写；`WORKLOG.md` 记**AI 做了什么**，每个需求一章。分开的原因：需求是证据，要原文留痕；工作记录是叙事，可以整理。

**为什么**：B9 出过真实事故——一句话提的需求，因为"太短没必要记"，在多轮对话后整条丢失，直到用户自己发现功能不存在。此后立规矩：**再短的需求也必须落 TODO 并写入档案**。另外，涉及 UI 的需求，完成时必须给截图自证，"我改了"不算数。

**REQUIREMENTS_LOG.md 骨架**（新条目插在最上面）：

```markdown
# 需求原文留痕（倒序，只增不改）

## 2026-07-28 R047
> （用户原话，一字不改，包括错字）
状态: 已交付 / 进行中 / 搁置    对应 WORKLOG: #047
```

**WORKLOG.md 骨架**（每需求一章）：

```markdown
## #047 标题（对应 R047）
- 背景/根因: 为什么要做，问题根因是什么
- 方案与取舍: 选了什么，放弃了什么，为什么
- 验证: 跑了哪些断言、界面上看了什么、截图路径
- 教训: 本次踩的坑（没有就写"无"，逼自己想过）
```

**最小落地**：第一天建两个空文件，然后把这段话加进系统指令：

```
每轮对话开始时：把我这轮的原话追加到 docs/REQUIREMENTS_LOG.md 顶部并编号。
每个需求完成时：在 docs/WORKLOG.md 增加一章（根因/取舍/验证/教训四段）。
需求再小也要记录。涉及界面的需求，交付时必须附截图。
```

[CC] Claude Code 的 TodoWrite 工具会自动管理任务清单，但**会话结束就没了**——双档案是它的持久化层，不能互相替代。**通用**：所有 AI 都写得了 markdown，此实践零门槛。

### 1.3 长期记忆库：把裁决和事故写成 AI 每轮能读到的规则

**是什么**：`memory/` 目录，一条经验一个文件，`MEMORY.md` 做一行式索引。与 WORKLOG 的区别：WORKLOG 记"发生过什么"（流水），记忆库记"以后要怎么办"（规则），后者才值得占用每轮上下文。

**单条格式**：

```markdown
# 缺失数据绝不填默认值
## Why（事故原文）
抓取无日期的新闻被填了"当前时间"，2024 年旧闻顶着今天的日期上了首页，
时效过滤器结构性失效——因为每条数据看起来都是新的。
## How to apply
- 缺失字段保持 NULL，在展示层处理，绝不在写入层造值
- QA 门禁对应断言: assert count(date IS NULL AND shown_on_home) == 0
## 相关
[聚合器时间戳不可信](aggregator-timestamps-untrusted.md)
```

**什么值得记 / 什么不记**：
- 记：用户的**裁决**（"不要碰服务器安全配置"）、事故换来的规则、反直觉的环境怪癖（"这个网关只有挂 VPN 能连"）、成本红线（"该 API 按条数计费，曾两天烧穿额度"）。
- 不记：代码细节（会过时）、一次性状态（"今天部署到了 v3"）、AI 自己能推出来的常识。判据一句话：**三周后新开一个对话，这条能不能防住一次事故或一次返工？不能就别记。**

**最小落地**：建目录 + 索引文件，向 AI 立规矩：

```
当我做出一个"以后都这样办"的裁决，或一次事故复盘出规则时：
在 memory/ 下新建一个文件（Why 含事故经过 + How to apply 含具体动作），
并在 memory/MEMORY.md 加一行索引：[标题](文件名) — 一句话摘要。
只记规则和裁决，不记流水。
```

[CC] Claude Code 有 auto-memory 机制，`MEMORY.md` 索引会自动进入每轮上下文，按需展开单条——上述目录结构就是照它的形状设计的。**通用做法**：把 `MEMORY.md` 索引全文粘进系统指令（Cursor rules / agent system prompt），单条文件让 AI 按需自己读。索引必须短（每条一行），否则挤占上下文。

### 1.4 版本号纪律：任何持久化的派生值必须带产出版本

**是什么**：一条铁律——凡是"由公式/prompt/模型算出来并且存进库里"的值（评分、标签、embedding、摘要），必须同行存一列**产出它的逻辑版本号**，且 QA 门禁断言全库版本一致。

**为什么**：还是 1.1 那个事故，值得单独展开：B9 改了排序公式，新数据用新公式，**存量 87% 的分数还是旧公式算的**。分数本身看不出新旧——都是合法的浮点数——于是排序效果测试测的是新旧混合的假象，结论全部作废。派生值不带版本号，等于给未来的自己埋一个不可见的定时炸弹。

**最小落地**：
1. 建任何派生值列时，同时建版本列：`score REAL, score_version TEXT`。
2. 算法写死引用一个常量（如 `SCORE_VERSION = "v3"`），写值时一起写入。
3. QA 门禁加断言：`SELECT count(*) WHERE score_version != '{当前版本}'` 必须为 0。
4. 改公式的标准动作序列：升版本号 → 回填存量 → 门禁转绿 → 才允许做效果评估。给 AI 的指令模板：

```
本次修改了 {公式/prompt}。执行版本纪律：
1. 升级版本常量并说明新旧差异
2. 回填全部存量数据（走 1.5 的三护栏脚本）
3. 跑 QA 门禁确认版本一致性断言通过
在第 3 步完成前，不许给我任何基于该字段的统计或结论。
```

评测用 prompt/人设同理：B9 的评测 agent 把版本号作为一切对比的前提——两次评测结果能不能比，先看版本号相不相同。

**通用**：纯工程纪律，与用哪家 AI 无关。

### 1.5 危险操作护栏：全库改写三护栏 + 每日备份

**是什么**：任何触碰全表/全库的写操作（回填、清洗、去重、迁移），必须用带三个护栏的脚本执行，禁止裸跑 UPDATE。

**为什么**：B9 的去重重构一次要改写近半数据（当时冗余率 48.7%），同期还有定时 pipeline 在写同一批表。裸跑等于在行驶的车上换轮胎。

**三护栏**：
1. **默认预演**：不带 `--execute` 只打印"将影响 N 行 + 20 行样例"，看过样例才真跑。
2. **写前快照 + `--restore`**：执行前自动 `CREATE TABLE t_bak_{时间戳} AS SELECT ...`，脚本自带一键回滚。两个实测坑：**restore 后别用 UPDATE 的 rowcount 验证成功**（值相同的行不计数，会误报失败），要比对内容抽样；**备份表的 collation/字符集必须与主表对齐**，否则 restore 时 JOIN 匹配悄悄失效。
3. **互斥锁**：跑前抢文件锁，让定时 pipeline 检测到锁就跳过本轮，避免改写和增量写并发交错。

给 AI 的指令模板（可直接粘）：

```
凡是影响超过 100 行的写操作，禁止直接执行 SQL。必须写成脚本并满足：
1. 默认 dry-run，打印影响行数和 20 行前后对比样例，我确认后才加 --execute
2. 执行前自动建带时间戳的备份表，并提供 --restore；restore 的成功验证
   用内容抽样比对，不用 rowcount
3. 通过文件锁与定时任务互斥
```

**每日备份 cron**（第一天就装上，SQLite 示例）。口径统一为：**每日全量备份保 7 天 + 每周备份保 4 周**，滚动清理由 cron 自动执行：

```
# 每日全量备份（每天 03:00）
0 3 * * * sqlite3 {数据库路径} ".backup {备份目录}/daily/db_$(date +\%F).sqlite"
# 每周日再留存一份周备
0 4 * * 0 cp {备份目录}/daily/db_$(date +\%F).sqlite {备份目录}/weekly/
# 滚动清理：日备保 7 天，周备保 4 周
30 4 * * * find {备份目录}/daily -name "db_*.sqlite" -mtime +7 -delete
30 4 * * 0 find {备份目录}/weekly -name "db_*.sqlite" -mtime +28 -delete
```

**通用**：与 AI 无关。恰恰因为 AI 生成 SQL 又快又自信，这套护栏才更必要。

### 1.6 生成器模式：doc == code，同一事实只允许一份源

**是什么**：任何"同一份信息要出现在两个地方"的场景——配置表 ↔ 文档、枚举 ↔ prompt 里的名单、公式 ↔ 说明文——都由**单一事实源 + 生成脚本**渲染，禁止手改生成物，QA 断言生成物与源一致。

**为什么**：B9 的真实事故——配置表里声明 Benzinga 的媒体权威分是 5 分，但 LLM prompt 里的媒体名单是另一份手写文本，里面没有它。于是 LLM 按聚合器口径给 Benzinga 打了 0.401（3400 余条实测均值），且全程不报错——**两处手写必然漂移，且漂移不报错**。手写的第二份不是备份，是定时炸弹。

**相邻教训（引注）**：即使名单只有一份，关键词排除本身也靠不住——B9 曾一天漏放三次语义上明显该排除的内容。关键词黑名单必须配一道 LLM 语义闸兜底；双语场景下，排除表和匹配窗口要双语各配一套。

**最小落地**：
1. 认定事实源（通常是配置表或一个 `config.py`）。
2. 写渲染脚本：LLM 要用的名单/枚举 → 由脚本从配置表渲染进 prompt 模板；对外文档 → 由脚本从代码/表生成 markdown。
3. 生成物头部固定加 `<!-- GENERATED FROM {源路径} — DO NOT EDIT -->`。
4. QA 门禁加断言：重新渲染一遍与现存生成物 diff 为空，不为空即门禁失败。
5. 给 AI 立规矩：

```
带 GENERATED 头的文件禁止直接编辑。要改内容就改事实源，然后重跑生成脚本。
新增任何"LLM prompt 里引用一份名单/枚举"的场景时，必须走配置表渲染，
不允许在 prompt 里手写第二份，并同步在 QA 门禁加一致性断言。
```

版本化配置表是它的近亲：策略参数存 `strategy_config` 表，每次修改新增一条快照、唯一 `active` 标记，回滚只切标记不删历史——和 1.4 的版本号纪律拼在一起，任何时刻都答得出"这个结果是哪个版本的哪套参数算的"。

**通用**：与 AI 无关，但在 AI 协作下权重更高——AI 改 A 处时不知道 B 处存在，是漂移的头号来源。

## 第二章 · 与 AI 协作的流程纪律

工具会换，纪律不换。本章的每条做法背后都有一次真实事故，事故编号不重要，重要的是：这些坑与具体某家 AI 无关，换成任何 agent 都会踩。通用做法直接写，仅适用于 Claude Code 的机制标注 **[CC]**。

---

### 2.1 需求下达法：说清楚，留原话，让 AI 复述

**① 原始需求原文必须单独落档，且由 AI 逐轮记录。**

事故：一条口头需求提完就聊别的去了，AI 的任务列表里从没出现过它，直到用户自己发现，这条需求已经整条凭空丢失。会话记录会滚走，TODO 是 AI 转述过的二手信息——只有用户原话是唯一可对账的凭证。

做法：项目根目录建 `docs/REQUIREMENTS_LOG.md`，倒序（最新在上）逐轮记录用户原话，AI 不得改写、不得概括。把这条写进项目级系统指令（Claude Code 放 `CLAUDE.md` **[CC]**，Cursor 放 `.cursorrules`，其它 agent 放系统提示词）：

```
每当我提出新需求或修改需求，你必须先把我的原话一字不改地追加到
docs/REQUIREMENTS_LOG.md（倒序，带日期和轮次号），然后用你自己的话
复述你理解的需求让我确认，确认后才开始动手。短需求、一句话需求同样适用。
```

复述确认不是客套：AI 理解偏了，在动手前纠正花 10 秒，在交付后纠正花一下午。

**② 截图自证，以及它的对称推论。**

档案里的硬规矩是交付方向的：凡涉及前端/UI 的需求，AI 完成时必须给出部署后页面的实际截图——"界面改好了"四个字不算数，截图算。反方向是这条规矩的对称推论（不是事故换来的，但同理成立）：你给 AI 报 bug 时，一张截图也比文字描述（"排序好像不对"）更能钉死现场——省去 AI 猜你看的是哪个页面、哪个区块、哪条数据。

**③ 分工要说破：AI 给数据，你拍板。**

排序策略调优时，用户原话是（引自需求档案 2026-07-29）：

> 所有因子做出来之后用你觉得合理的方式排序。但排不对也没关系。都放到策略实验室里（正常因子和加分项稍微分开），我自己调整。

这段话极大解放了双方：AI 不必反复猜测主观偏好，把力气花在保证实验室工具与生产**同公式、同取数路径**——这是 AI 的责任，也是一条硬规则：实验工具禁止私带公式副本，否则就是 1.4 那类不可见漂移（87% 存量旧公式分数的事故证明，这种漂移从任何界面都看不出来）；用户只在自己有判断优势的环节介入。可直接复用的分工声明：

```
涉及主观判断（排序口味、文案、优先级）的部分，你不要替我决定，
把候选项和数据摆出来，做成我能自己调的工具，我来拍板。
你的责任是保证工具里的数据和生产环境完全一致。
```

---

### 2.2 验收法：AI 说完成不算完成

**① 完工标准 = 用户界面上验证过。**

B9 用六次事故换来这条铁律：数据落表了但前端没显示、接口通了但页面报错、部署了但缓存没刷新……"落表≠交付"。验收动作固定为：部署后打开浏览器把全站主要页面过一遍，并做孤儿数据审计（表里有但界面上永远展示不出来的数据，等于没有）。

**② 眼球测试是底线，QA 全绿不豁免。**

事故：QA 脚本断言全部通过的同一天，人眼三次当场抓出断言没拦住的问题。另一次独立事故里，2024 年的旧闻顶着今天的日期上了首页——根因是缺失日期被填了默认值（见 1.3 的记忆条目），机器断言和肉眼都该防它。断言只能覆盖想到过的问题，人眼能覆盖没想到的。交付前的固定动作：**肉眼扫一遍首屏 + 把可疑数字拿去搜一下**。这条同样约束 AI：

```
宣布"完成"之前，你必须：1) 打开实际页面截图给我；2) 对首屏内容做一次
常识检查（日期是否合理、数字是否可信、有没有明显不该出现的内容）；
3) 跑完QA门禁并贴出结果。三者缺一不得说"完成"。
```

**③ 报数字前先对口径。**

严重事故：AI 把"SQL 能取到 400 行"报成"缓存可用 400 条"，实际可用 0 条——查询结果和用户关心的指标根本不是一个东西。规矩：AI 汇报任何数字，必须附带口径三件套——**这个数字从哪查的、统计的是什么范围、和你要的指标是不是同一个东西**。你听到任何一个"成果数字"，先问一句"这个数怎么算出来的"，再决定信不信。

**④ 核对用精确标识，不用模糊匹配。**

事故：验证新闻召回率时，AI 用关键词反查标题，但 LLM 在处理时会意译标题，关键词匹配不上，把实际 70% 的召回率报成了 45%——差点为一个不存在的问题返工。核对两份数据是否对上，用 URL、ID 这类精确不变的字段回查，永远不要用标题、名称等会被改写的字段。

### 2.3 成本治理：授权边界白纸黑字

**① 接入任何计费 API 前，先查清计费模型。**

事故：接入 X API 时误以为按请求次数计费，实际按**返回的推文条数**计费，两天烧穿整月额度，402 报错全线停摆。之后的规矩：接入前必须书面回答三问——**按什么计费（次数/条数/token/时长）？单价多少？我们的调用模式下日成本估算多少？**——答不出就不许上线。上线后按计费单位做预算控制（B9 是每轮 150 条硬顶）。

**② 授权边界写进系统指令，而不是每次口头交代。**

```
成本授权边界：
- 可自主：单次预估成本 < {如 $1} 的API调用；用你自己的推理能完成的分析、
  评测、复核、成文工作（不许为此调用外部LLM API）。
- 需事前报备：新接入任何计费服务；单日预估成本 > {如 $10} 的批量任务。
- 绝对禁止：在未确认计费模型前发起批量调用。
```

**③ 设计贵路径与便宜路径，默认走便宜的。**

B9 的分层：判断力任务（分析、裁决、成文）由主 AI 自己做；批量重活（打分、清洗、标注）优先走公司内部网关的便宜模型；再往下还有"Mac 闲时算、云 VM 兜底"的免费算力层。原则：**每类任务显式指定路径，且贵路径要有降级方案**（网关连不通时回退什么、限速 30req/min 时怎么排队）。反向的省钱纪律同样重要：预估级别的统计（成本估算、市值排序）明确告诉 AI "到预估精度就停"，不要让它把便宜任务做成贵任务。

---

### 2.4 节奏控制：并行、换挡、抽查

**① 能并行就并行，一句话授权。**

独立任务默认并发，把这句写进系统指令即可："多个互不冲突的任务默认并行执行，有共享资源冲突的才串行，不必每次问我。" Claude Code 可用 subagent 并行 **[CC]**（通用替代：开多个会话/多个 agent 实例，各领一个独立任务）。附带一个真实的坑：并行 agent 同时 SSH 同一台服务器会打爆连接槽位，connection refused 会被误判成服务器宕机——并行前先确认共享资源（SSH 连接、数据库锁、API 限额）扛得住，SSH 场景配 ControlMaster 复用连接。

**② 模型档位切换：判断权委托给 AI，条件是当场如实报告。**

Lawrence 的裁决是：把档位判断权交给 AI，前提是如实报告——任务需要更强的模型时要主动说、主动换，而不是默默用弱档位硬扛把活干砸。委托模板（各家 AI 的模型选择机制不同，Claude Code 内可直接切换档位 **[CC]**，其它工具则由 AI 提示你手动切换）：

```
模型档位切换由你判断并直接执行，但必须当场如实报告切换动作和理由，
不许默默用弱档位硬扛。
（可选收紧：把"由你判断并直接执行"改为"由你判断、经我审批后执行"。）
```

**③ 抽查时机：AI 宣布"自检全绿"之后，恰恰是你该介入的时刻。**

统计事实：B9 三次用户当场抓出 bug，全部发生在 AI 自检通过、宣布完成之后。这不是 AI 偷懒，而是自检只能验证"想到过的问题"。所以人的抽查不可省，且时机固定：**每次 AI 宣布部署完成/QA 通过，你立刻花 5 分钟亲手点开界面**——首屏扫一眼、可疑数字搜一下、核心链路点一遍。抓到问题当场打断，别攒着：纠偏成本随时间指数上涨，当场说是改一行，第二天说可能要回滚一天的构建。

### 2.5 事故后动作：三件套缺一不可

每次事故后必须完成三件事，只做其中一两件等于没做：

**① 复盘进 WORKLOG。** `docs/WORKLOG.md` 每个需求/事故一章，固定四段：**根因 / 取舍 / 验证方式 / 教训**。这是给"未来查这段历史的人（和 AI）"看的，写清楚为什么当时这么改。

**② 抽象进长期记忆。** WORKLOG 是流水账，记忆是抽象出的可复用规则。Claude Code 用户放 auto-memory（`MEMORY.md` 索引 + 每条一个文件，写明 Why 和 How to apply）**[CC]**；其它 AI 用户把规则追加进系统指令文件，效果等价。关键是**抽象**：记"改公式必查存量版本一致性"，而不是记"7 月那次公式改错了"。

**③ 机制化防复发。** 光记住不够，要把教训变成机器强制执行的东西。完整案例：发现全库 87% 的分数还是废弃旧公式算的且界面上不可见——复盘写进 WORKLOG（根因：改公式时没有回填存量）；抽象成记忆（改公式必查存量一致性，否则效果测试是假的）；机制化落地为**给分数表加公式版本号列 + QA 门禁增加逐行版本断言**。此后同类问题在 QA 阶段自动拦截，不再依赖任何人记性。

三件的分工：WORKLOG 防"忘记发生过什么"，记忆防"换个场景再踩同类坑"，机制防"记住了但没执行"。B9 的 QA 门禁就是这样从 0 条断言长到 120 条的——每条断言背后是一次不想再经历的事故。

事故后收尾自查清单（可直接发给 AI 执行）：

```
本次事故收尾，逐项完成并贴出证据：
1. WORKLOG.md 新增一章：根因/取舍/验证/教训
2. 抽象出可复用规则，写入长期记忆（或系统指令文件），含Why和适用条件
3. 说明机制化措施：新增了哪条QA断言/护栏脚本/配置约束，防止同类问题复发
4. 如果第3条你认为"无法机制化"，说明理由，由我裁决是否接受
```

---

**本章一页纸**：原话落档、复述确认、截图自证；界面验证、眼球测试、口径对齐、精确回查；计费先查清、边界写明白、贵活走便宜路；并行授权、换挡委托、全绿后必抽查；事故后 WORKLOG+记忆+机制三件套。做法都不复杂，难的只是每次都做——所以把它们全部写进系统指令和 QA 门禁，让机器替你坚持。

## 第三章 · 可直接复制的 Prompt 模板库

本章模板全部来自真实事故的反向工程：每一条约束背后都有一次翻车。使用方式：整段复制进对话，替换占位符后发送。**占位符统一用花括号，分两类记号**：`{描述}` 为必填占位符，必须替换成你的实际值；`{如 xxx}` 为带建议默认值的占位符，可直接采用建议值，也可替换。模板语言刻意写成通用指令，Cursor / Copilot / 任意 agent 都能直接吃；只有标 **[CC]** 的部分依赖 Claude Code 专属机制，用别家 AI 时按备注替换。

---

### 3.1 新项目开工/接手模板

**适用时机**：任何新项目第一条消息，或接手存量项目的第一条消息。
**事故背景**：曾因没留需求原话丢过整条需求；曾六次把"数据落表了"当成"交付了"，最后被迫立下"界面验证过才算完成"的铁律——这些基建在写第一行业务代码前就该存在。

```
你将作为我的工程协作AI参与项目 {项目名}。在写任何业务代码之前，先完成以下基建，逐项汇报文件路径：

1. 建立双档案：
   - docs/REQUIREMENTS_LOG.md：逐轮倒序记录我的需求原话（原文粘贴，禁止改写），每条带日期和状态（进行中/已完成/已验证）。
   - docs/WORKLOG.md：每个需求一章，固定四节：根因分析 / 方案取舍 / 验证方式 / 教训。
2. 建立QA门禁脚本 {如 scripts/qa_gate.py}：可反复执行的断言集合，初始至少覆盖：服务存活、核心接口鉴权、关键数据时效红线。之后每次事故修复必须新增对应断言，只增不删。
3. 建立备份机制：数据库每日全量备份保 7 天 + 每周备份保 4 周，含滚动清理，写成定时任务，并把恢复命令写进 docs/WORKLOG.md。
4. 约定完工标准：任何需求，只有在用户可见界面上验证通过、且QA门禁全绿，才允许说"完成"。
5. 缺失数据绝不填默认值（尤其时间字段），宁可置空并向我上报。

确认理解后，用一段话复述以上规则，再开始干活。
```

使用说明：接手存量项目时在开头加一句"先通读代码库，把现状如实写进 WORKLOG.md 第一章，再执行以上步骤"。[CC] Claude Code 用户可另建 CLAUDE.md 存放这些规则，使其每轮自动生效（通用替代：放进 Cursor 的 `.cursorrules` 或其它 agent 的系统提示词）。

---

### 3.2 需求登记模板

**适用时机**：每提出一个新需求时，包括一句话的小需求。
**事故背景**：真出过事故——一条一句话需求在多轮对话中被整条遗忘，事后连"当初到底要什么"都无法还原。短需求也必须走这套流程。

```
新需求登记。以下原话必须原文写入 docs/REQUIREMENTS_LOG.md，禁止改写、禁止省略：

"""
{需求原话}
"""

登记后做三件事，做完再动手：
1. 用你自己的话复述这个需求，包括你理解的验收标准；
2. 列出完整TODO清单——验证步骤也是TODO，不只是开发步骤；
3. 指出你认为有歧义、或我可能没想到的点。
我确认复述无误后，你才开始实现。UI类需求完成后必须给截图自证。
```

使用说明：三引号里的内容就是留档的法定原文，改需求时重新走一遍本模板，旧条目标记状态而不是覆盖。

---

### 3.3 QA 门禁验收指令

**适用时机**：每轮改动完成、准备说"做完了"之前。
**事故背景**："必须拿到 no bug 报告才算交付"是用户在多次带伤交付后立下的规矩；B9 的门禁最终积累到 120 条断言，覆盖鉴权、时效红线、公式一致性。

```
本轮改动自检。执行 {QA门禁脚本路径}，要求：
1. 贴出完整输出，不许只贴摘要；
2. 有任何失败：先修复再重跑，循环到全绿。不许跳过、注释掉或放宽断言；确需修改断言本身，先向我说明理由并获同意；
3. 本轮改动如引入新的可断言事实（新接口、新红线、新公式、新配置），把对应断言补进门禁脚本；
4. 最终给我明确结论："QA门禁 {断言总数} 条断言全绿，无bug报告"。拿不到这句话不算交付。
```

使用说明：把它设为固定收尾动作——每轮交付对话的最后一条消息就是这段。

---

### 3.4 全库/批量改动护栏指令

**适用时机**：任何一次性触碰大量存量数据的操作——回填、清洗、公式重算、去重。
**事故背景**：真实翻过的三个坑全在这里：恢复逻辑信了 UPDATE 的 rowcount 结果没真恢复；备份表 collation 与主表不一致导致比对失效；改完公式才发现 87% 的存量分数还是废弃公式算的且外表看不出来。

```
接下来对 {表/数据范围} 执行批量改动：{改动描述}。按以下护栏执行，缺任何一步就停下来问我：

1. 预演优先：脚本默认 dry-run，只输出"将影响 {N} 行 + 随机抽样20行的前后对比"，不落盘。我看过预演并明确回复"执行"后才允许真跑。
2. 写前快照：真跑前把受影响数据完整备份到快照表（表结构、collation与主表严格一致），并提供 --restore 参数一键恢复。
3. 恢复验证：恢复成功与否不许用 UPDATE rowcount 判断，必须查询实际数据核对。
4. 互斥锁：执行期间锁住相关pipeline，防止并发写入污染。
5. 版本一致性：如果改的是公式/评分逻辑，给结果加版本号列，跑一条SQL统计存量数据各版本占比，旧版本残留必须重算或向我说明。
6. 完成后报告：实际影响行数 vs 预演预估，对不上必须解释原因。
```

使用说明：把第 1 条的"我明确回复执行"当成硬闸门——AI 替你按下执行键之前，你必须亲眼看过预演 diff。

---

### 3.5 复盘与记忆提取指令

**适用时机**：一次事故处理完毕后，或每周固定做一次。
**事故背景**：33 条长期记忆是 B9 两个月真实事故的全部沉淀；没有这套提取流程，同一个坑（比如关键词反查召回率）会隔几周再踩一次。

```
现在做复盘与记忆提取。回顾 {时间范围/某次事故}，流程：
1. 从 docs/WORKLOG.md 和本次对话中找出：真实发生的事故、被推翻的方案、我做过的裁决；
2. 每条提炼为独立记忆条目：一句话结论（标题）/ 事故经过（Why）/ 下次怎么做（How to apply）/ 关联条目链接；
3. 写入 {记忆目录}，并更新索引 {索引文件}——索引每条一行：标题+一句话摘要；
4. 只收"再来一次会做得不同"的具体教训，不收"要更仔细"这类空话；
5. 列出新写的条目清单，由我裁决去留。
```

使用说明：[CC] Claude Code 有跨会话自动记忆目录（MEMORY.md+每条一文件），可直接指向它；其它 AI 用 `docs/lessons/` 普通目录同样成立，只是要在每次开工时手动喂给它索引文件。

---

### 3.6 交接文档生成指令

**适用时机**：项目要交给同事、外包或另一个 AI 接手时。
**事故背景**：B9 的排序公式改过多版、配置散在快照表里、部分表的时间戳来源不可信——这些"只在 AI 和我脑子里"的知识，不写下来就等于不存在。

```
生成一份交接文档，读者是 {接手人，背景：完全不了解本项目}。要求：
1. 系统全貌：分几层、各层职责、数据流向，配一张文字架构图；
2. 数据字典：每张核心表——存什么、谁写入、谁消费、坑在哪（来源不可信的字段、语义有歧义的列必须显式标注）；
3. 判分逻辑：{核心公式/排序逻辑} 的当前版本号、公式本体、配置存在哪张表、如何回滚到历史版本（回滚不删历史）；
4. 运维手册：部署方式、备份与恢复命令、QA门禁怎么跑、常见故障与处置；
5. 已知债务与未完成项：从 WORKLOG.md 和 TODO 如实汇总，不许美化。
写完自查：一个没参与过项目的人，能否只靠这份文档独立完成一次发布+一次回滚？不能就补到能为止。
```

使用说明：验收时随机挑文档里一条恢复命令实际执行一次，跑不通就整份打回。

### 3.7 数字核对指令

**适用时机**：让 AI 汇报任何指标、进度数字、成果数字之前——建议直接进常驻规则。
**事故背景**：严重事故——AI 把"SQL 取到 400 行"报成"缓存可用 400 条"，实际用户可用 0 条；口径滑移在汇报里是察觉不出来的。

```
向我汇报任何指标/数字，必须附带以下三项，缺一项不许报：
1. 口径定义：这个数字统计的到底是什么？（正例："缓存表中 status=ready 且未过期的行数"；反例："缓存有400条"）
2. 取证命令：得出该数字的原始命令/SQL，保证我原样复跑能得到同一个数；
3. 与结论的距离：这个数字距离"用户实际可用/业务实际达成"还差哪些环节，每个环节是否确认过。
如果你的口径与我问题的口径不一致，先声明差异再报数，禁止静默换口径。
```

使用说明：验证召回/覆盖类指标时追加一句："回查必须用URL等唯一标识精确匹配，禁止用关键词模糊匹配"——曾因 LLM 意译标题，关键词反查把 70% 的召回报成 45%。

### 3.8 眼球测试验收指令

**适用时机**：部署上线后、宣布交付前的最后一步。
**事故背景**：曾一天之内被用户抓出三次"QA 全绿但一眼假"的问题；另一次独立事故中，2024 年的旧闻顶着今天的日期挂上首页（根因：缺失日期被填了默认值）。断言只能覆盖想到的错，人眼负责没想到的。

```
部署完成后做一轮"人眼验收"，QA脚本全绿不能替代这一步：
1. 打开 {前端地址}，逐页过首屏：日期是否合理（有无旧内容顶着今天的日期）、排版是否破损、有无明显不该出现的内容混入；
2. 从页面上挑 {如 3-5} 个具体数字/标题反查：数字回数据库查原始记录，标题拿去搜索引擎搜，确认真实存在且信息一致；
3. 任何"正常人一眼能看出"或"随手一搜就穿帮"的问题，视为验收失败，修完从第1步重来；
4. 全部通过后，给我每个页面的截图作为验收凭证。
```

使用说明：[CC] Claude Code 可用内置浏览器工具自己截图自证；无浏览器能力的 AI，让它输出上述核查清单（含具体 URL 和待查数字），由你人工执行五分钟。

### 3.9 迁移头部指令（十条铁律）

**适用时机**：换用任何新 AI 工具（Cursor、Copilot、其它 agent）时，粘贴进其系统提示/自定义指令，一次性注入本手册核心纪律。

```
你是我的工程协作AI。铁律：
1. 需求原话原文存入 docs/REQUIREMENTS_LOG.md 逐轮留档；动手前先复述需求+列TODO（含验证步骤），经我确认。
2. 完工标准=用户可见界面验证通过+QA门禁脚本全绿；"代码写完/数据落表"不叫完成。每次事故修复后往门禁加对应断言。
3. 缺失数据绝不填默认值（尤其时间字段），置空并上报。聚合来源给的时间戳视为不可信。
4. 批量/全库改动：默认dry-run预演，我确认后才真跑；写前建快照并提供一键恢复，恢复成功与否查实际数据而非rowcount。
5. 改公式/配置后必查存量数据版本一致性，公式结果带版本号。
6. 汇报任何数字前，先给口径定义+可复跑的取证命令；召回类验证用唯一标识精确回查，不用关键词。
7. 交付前肉眼扫首屏+抽查可疑数字反查来源，一眼假=验收失败。
8. LLM用到的名单/枚举必须由配置表渲染进prompt并加断言钉死，禁止两处手写。
9. 每次事故写一条教训入 docs/WORKLOG.md。
10. 如实报告不确定性，有歧义先问，禁止静默假设。
```

使用说明：这是全手册的最小可迁移子集——新工具哪怕只注入这十条铁律，也能避开 B9 踩过的大部分深坑；其余细节等它撞到具体场景时，再按前八个模板逐个投喂。
