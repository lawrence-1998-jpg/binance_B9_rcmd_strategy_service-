## 阶段一：先把数据底座立起来（07-26 ~ 07-28）

**起点**：一个能抓 RSS 的爬虫 + 一张表。问题很快暴露：同一件事被五家媒体报道，
库里就是五条；标题措辞一变，去重就失效。

关键决定：

- **事件 ID 用稳定指纹，不用标题 hash**。指纹取"主体 + 动作 + 日期"，
  不依赖 LLM 每次措辞。标题 hash 的问题是 LLM 改一个字就变成新事件。
- **去重换成真 embedding**（256 维，cosine ≥ 0.82）。原来用 TF-IDF，
  中英混排、同义改写完全抓不住。阈值 0.82 是实测标定的——文档里写的 0.65 是错的，
  照抄会让去重形同虚设。
- **入库前做跨轮归并**：写库前拿指纹比对历史，命中就合并信源而不是新增一行。

这个阶段修掉了 48.7% 的库内冗余。

## 阶段二：从"加密新闻"扩到"全球市场"（07-28 ~ 07-29）

老板的反馈是：只有币圈新闻，热度感和 CNBC 这类友商差太远。

于是：

- 召回范围扩到美股 / 港股 / 日股 / 韩股 / 宏观政策（明确排除 A 股），
  新增 `market_scope` 标签维度，系统提示词从"加密新闻分析师"重写为"全球市场分析师"。
- 接入 dxFeed、Massive/Benzinga 等机构新闻源。

**随即撞上第一个真正的坑**：韩股新闻全排在最前面。

查下去发现根因不是权重没调好，而是**档位是相对"自己所在市场"判定的、排序却是全局的**
——韩股的 S 档率是美股的 90 倍。修法是引入市场重要性倍率（美股提权、日韩港降权），
并在策略实验室开放参数栏让人直接调。

## 阶段三：时效性事故与信源可信度硬闸（07-29）

用户截图问："这条数字服务税是 6 月底的事，怎么在库里？"

根因链条比想象的长：

1. 搜索聚合器（GoogleNews 等）返回的是**分发时间不是发布时间**，且不给正文；
2. `normalize_published_at` 遇到"无日期"时回落成**当前时间**——等于伪造新鲜度；
3. 下游所有日期校验因此结构性失效。

修复不是补一个 if，而是：

- 新增 `crawler/source_trust.py` **信源可信度硬闸**，在 LLM 之前拦截；
- 新鲜度窗口 7 天 → 5 天；
- 清理存量 742 条聚合器孤证（清理前先用搜索验证"重要新闻有可信信源冗余覆盖"，
  确认删除不会丢真新闻）。

沉淀成一条规则：**缺失数据绝不填默认值**。把"不知道"写成"现在"，是所有下游校验失效的源头。

## 阶段六：成本硬闸与交易实体（08-02）

两件事同时做。

**成本硬闸（ADR-002 块 A）**：个人 API key 余额告急，要求"关掉开关后整套架构一分钱都不能花"。

- 9 个付费调用点收敛到**单一收费闸口** `crawler/llm_gate.py`；
- **fail-closed**：任何 DB / 解析异常都当作"不允许花钱"；
- 开启必须带自动失效时间（默认 6h，上限 24h）；
- 断供时条目**延后而不是丢弃**——这里修过一个严重 bug：第一版把被闸拦下的条目
  标记成了已消费，等于**永久数据丢失**。是从真实运行日志里看到 `marked 4 items consumed`
  才发现的，只读代码看不出来。

**交易实体（ADR-002 块 B）**：老板反馈"刺激标的物交易的感觉不足"。

- 三级阶梯抽取可交易标的：编辑给的 ticker（零成本）→ 币种 binance_spot 校验 → 标题匹配；
- 标题后以 tag 展示，并新增"交易实体加成"加分项；
- 模块定位从"新闻 agent"改为"**事件 agent**"。

过程中发现 Benzinga 的 ticker 一直被丢弃——接回来后美股实体覆盖 43 倍提升，且零成本。

## 阶段七：冲击力因子的根治（08-02 ~ 08-03）

一个很有代表性的教训。

任务是判断"标题里这个百分数是不是价格涨跌幅"。用正则 + 排除词表做了四轮：

```
v1 关税/税率 → v2 同比/购金 → v3 税/覆盖/超预期/目标价 → v4 opt-in 反转口径
仍然漏："份额升至 67.4%"、"市占率升破 58%"
```

第四轮时停下来想清楚了：**规则必然输**。因为"百分比能表示什么"是无穷集合
（支持率/市占率/覆盖率/税率/收益率/波动率…），而"升/降/涨/跌"这些动词能修饰任何指标——
要问的是这个数字**度量什么**，那是语义不是模式。

改法：让**已经在读全文的 LLM** 多输出一个结构化字段 `price_move`
（`is_price_move` / `move_pct` / `move_horizon`）。实测真实网关 12/12，
包括"收益率升至 5.26%（水平≠变动）"这类规则完全无解的边界。
**存量回填发现原本 60% 被误判。**

正则兜底保留——存量数据没有新字段，删了会让它们集体归零，是一次无声的全库降级。

## 阶段八：三天停摆（08-02 ~ 08-04）

**最贵的一课，不是修复贵，是三天没人知道它坏了。**

现象：网站轮次停在 08-01，大盘情绪空白，用户自己发现的。

根因：Mac 上的 enrich worker **从装上那天起一次都没成功跑过**。
`~/.b9/local_enrich_worker.py` 是指向 `~/Desktop` 的软链，
而 macOS TCC 保护该目录、launchd 没有 Full Disk Access，每 5 分钟 EPERM 一次。
装的时候只确认了"文件在、plist 注册了"，没等它自然触发一次看结果。

**为什么三天零告警**：

| 现象 | 日志级别 | 为什么骗过监控 |
|---|---|---|
| 每轮 `personal_key_disabled: 801` | INFO | 行为**完全正确**（fail-closed，个人 key 分文未花） |
| 积压涨到 11,264 条 | WARNING | 只是"积压多"，不是"停产" |
| `enriched: 0, events: 0` | INFO | 与"本轮没新数据"长得一模一样 |

**"按设计延后"与"下游已死"在日志里无法区分。**

修复与防复发：

- 软链换实体副本；
- 同优先级取数由 FIFO 改为**新的先做**——原 FIFO 会先啃两天前的稿子，
  队列在追平但**产品仍是坏的**（大盘情绪取 24h 窗口一直算不出来）；
- worker 改边算边交（每 40 条 flush），避免整批算完才提交导致的相位扑空与崩溃损失；
- **新增端到端健康判据**：判的不是"组件活着吗"而是"最近还有没有真的产出事件"，
  首页最顶加停摆横幅，红了直接写明排查顺序。

积压从 11,264 条回补至清空，全程个人账号花费 **$0.0000**。

## 贯穿始终的几条工程教训

这些是反复付出代价后固化下来的：

1. **落表 ≠ 交付**。完工标准是"在用户界面上验证过"，不是"接口返回 200"。
2. **报数字前先对齐口径**。曾把"SQL 取到 400 行"当成"缓存可用 400 条"报成果，实际可用 0 条。
3. **加列必须走完五个环节**：SQL 投影 / 计算 / 请求解析 / 响应序列化 / 前端渲染。
   缺任何一个都静默失效——这一条栽过 5 次。
4. **验证写库真的成功**，不只看返回码。曾因少一个占位符导致全部写入静默失败，
   只打 warning 返回 0，差点当成"没新数据"。
5. **聚合覆盖率会掩盖首屏**。曾报"美股覆盖涨 18 倍"而首屏 0/10 有标签。
6. **定时任务装完必须确认它真的成功跑过一次**。注册成功 ≠ 跑起来。
7. **导出副本会盖住线上的缺陷**。为自包含而补的依赖，正好是线上缺的那个。
