---

## 一、目标

从 8 类渠道并行抓取加密货币 / 美股 / 高相关科技新闻的**原始条目**，做统一格式化和最基础的预处理，供下游聚类与理解模块消费。本 PRD 不涉及"这条新闻是否重要""是否和别的新闻是同一件事"——那是 PRD-02 的工作；这里只保证**原始数据完整、干净、字段统一**。

---

## 二、数据源清单（8 类，Demo 阶段已验证可用）

| # | 渠道 | 接入方式 | 数量 | 说明 |
|---|---|---|---|---|

## 三、各渠道原始字段规范

### 3.1 通用字段（RSS / HTML / 搜索引擎 / 日历，统一为一种中间格式）

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `title` | string | 是 | 原文标题，不做任何改写 |
| `url` | string | 是 | 原文链接，去重的关键字段之一 |
| `published_at` | ISO8601 datetime | 是 | 原文发布时间；缺失时用抓取时间兜底，并打 `time_missing` 标记 |
| `source_name` | string | 是 | 信源名称（如 "CoinDesk"、"吴说区块链"） |
| `source_channel` | enum | 是 | `rss` / `rsshub` / `html` / `search` / `market_signal` / `calendar` 之一，对应上表 8 类 |
| `authority` | int 1-5 | 是 | 人工预设的信源权威分（配置在信源注册表里，不是每条现算） |
| `lang` | enum | 是 | `zh` / `en` |
| `raw_body` | text | 否 | 正文全文/摘要，能拿到就存，供 PRD-02 做结构化理解用 |
| `fetched_at` | datetime | 是 | 本次抓取时间（UTC+8） |

### 3.2 X（Twitter）专属字段

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| `tweet_id` | string | 是 | 唯一 ID，主键 |
| `kol_username` | string | 是 | 账号名 |
| `kol_display_name` | string | 否 | 展示名 |
| `kol_followers_count` | int | 是 | 粉丝数，用于未知账号的权威分兜底判断 |
| `kol_verified` | bool | 否 | 是否认证账号 |
| `tweet_body` | text | **是，必须存全文** | 见下方「转发去重」，全文本是判断转发的唯一依据 |
| `tweet_url` | string | 是 | 推文链接 |
| `tweet_lang` | string | 否 | X API 自带的语言标记 |
| `like_count` / `retweet_count` / `reply_count` / `quote_count` / `impression_count` | int | 是 | 互动量，供后续热度信号使用（PRD-02 之外） |
| `published_at` | datetime | 是 | 推文发布时间 |
| **`is_repost`** | bool | **是（新增，本期必须做）** | 见下方「转发去重」，本条是否判定为转发/转载 |
| **`repost_type`** | enum | **是（新增，本期必须做）** | `original` / `retweet` / `quote` / `text_repost`，见下表 |

`repost_type` 取值定义：

| 值 | 判定依据 |
|---|---|
| `original` | 既非 API 结构化转推，也未命中正文重复判定 |
| `retweet` | X API 原生转推（`referenced_tweets[].type == "retweeted"`），**建议在抓取请求阶段直接过滤掉，不落库**（见下） |
| `quote` | X API 引用推文（`referenced_tweets[].type == "quoted"`），**落库但打标**，正文里引用部分和评论部分建议分开存（`quoted_tweet_id` 单独一列） |
| `text_repost` | 无 API 结构化标记，但正文与另一条已入库推文高度相似（复制粘贴 / 手动加 "RT @xxx:" 的老式转发），**落库但打标** |

## 四、必须的预处理

### 4.1 X 内容去重（本期必须做）

**问题背景**：一条快讯常被十几个搬运号在几分钟内原样转发或轻微改写转发，`tweet_id` 各不相同但正文本质是同一条内容。如果不处理，会有两个后果：
1. 十几条一起塞进下游 LLM 结构化，浪费成本；
2. 更严重的——如果 PRD-02 的"独立信源计数"不知道这是同一条内容，会把转发量误算成信源广度（这是 2026-07-27 产品侧明确提过的真实问题，见 PRD-02 的更新规则）。

**要求**：

1. **单次抓取内的正文去重**：同一批抓取结果里，对 `tweet_body` 做归一化后完全一致的，只保留一条（保留权威分最高或粉丝数最多的账号）。归一化规则：去掉 URL、@提及、#话题标签，转小写，去标点，截断到前 120 字符做 key。
2. **URL 去重**：正文里如果只是分享一个外部链接、几乎没有自己的文字（例如"吴说 X 帖仅分享外部链接"这类），按 `url` 做去重，同一个外部链接在同一批次内只保留一条。
3. **原生转推（Retweet）在请求层直接排除**，不进入落库流程——X API 支持在查询参数里加 `exclude: retweets` / `-is:retweet`，成本最低，做在这一层。
4. **引用推文（Quote Tweet）和手动文本转发不能在抓取层排除**（内容有可能带评论、有增量信息），必须**落库但打上 `is_repost=true` / `repost_type` 标记**，交给下游 PRD-02 的独立信源计数逻辑处理，不能在这里直接丢弃。

### 4.2 通用条目去重

- 同一抓取批次内，`url` 完全相同的只保留一条。
- 不同信源转载同一篇稿子（常见于聚合站）——**本期不要求识别**，这是 PRD-02 语义聚类要做的事，抓取层只需要保证原始条目本身没有字面重复。

### 4.3 时间处理

- 所有时间戳统一转换并存储为 **UTC+8**，不要存 UTC 再指望下游转换（历史上这个坑真实踩过——见 `crawler/timeutil.py` 的教训：改时区如果只切系统时区、不改代码里的时间戳生成逻辑，会导致数据时间和实际调度时间对不上）。
- 缺失 `published_at` 的条目要显式标记，不能用抓取时间悄悄顶替而不留痕迹。

## 五、调度频率

| 任务 | 频率 | 说明 |
|---|---|---|
| 主抓取（全部 8 类渠道） | 每天 2 轮，08:00 / 20:00（UTC+8） | 与下游 LLM 处理频率一致 |
| 高频存档（仅限成本低的源：RSS/HTML） | 每 2 小时 1 次 | 只存档不处理，处理仍按 12 小时批量跑，用于防止两轮之间的新闻被 RSS 源自然滚动挤出去 |

## 六、验收标准

1. 8 类渠道全部能稳定抓取，任一渠道连续断 2 轮要能被监控发现（不要求本期做告警系统，但要求日志/记录里能看出"这轮这个渠道抓了 0 条"）。
2. X 数据的 `is_repost` / `repost_type` 字段有值，且原生转推（retweet）已在抓取请求层排除、不落库。
3. 抽样验证：同一批次内故意构造的"10 个账号转发同一条"场景，落库后应该只有 1（或按去重规则应留的条数）条打了非转发标记，其余打 `repost_type=text_repost` 或 `retweet`（若为原生转推则应完全不落库）。
4. 所有落库时间戳为 UTC+8，无 UTC/UTC+8 混用。
