# Skill 02 · 时效性衰减（freshness）

> **一句话**：「这条新闻有多新」不是事件的固有属性，是**「你什么时候看它」的函数**——所以它必须在查询时算，不能落库。

---

## 1. 一条人眼一看就知道错的首屏结果

2026-07-30 中午实测首屏：

| 位置 | 内容 | 发布日 |
|---|---|---|
| #11 | 美伊缓和致油价跌 16% | 7/28 |
| #13 | 布伦特原油日内暴跌 7.71%，跌破 86 美元 | 7/27 |

而**当天的真实新闻**是「美军称已完成对伊朗大规模打击」「埃及附近油船起火，油价涨 8%」
—— 局势升级、油价**上涨**。两条 2–3 天前、且**已被事态反转**的旧叙事，压在当天真实事件前面。

## 2. 根因

`score_timeliness` 按 24h 半衰期算，**公式本身没问题**，
但它算完就写进 `news_events.score_timeliness`、加权进 `importance_score` 一起落库，**此后再也不重算**。
每条内容都是"抓到当时还很新"，所以实测：

| 事件 | 入库日期 | 存量 T |
|---|---|---|
| 布伦特原油暴跌（3 天前） | 7/27 | 0.973 |
| 美伊缓和油价跌 16%（2 天前） | 7/28 | 0.960 |
| 美军完成对伊朗打击（当天） | 7/30 | 0.980 |

**3 天前的内容 T=0.973，当天的 T=0.980 —— 时效因子在排序里几乎不产生任何区分度。**

于是排序完全由影响力/热度决定，而**旧事件恰恰在这两项上占便宜**：
它多出 2–3 天时间通过跨轮归并累积信源（热度的一半就是独立信源数），越老信源越多、分越高。
**系统结构性地偏向旧闻。**

---

## 3. 做法

```python
HALFLIFE_HOURS  = 48      # env: B9_FRESHNESS_HALFLIFE_H
MIN_MULTIPLIER  = 0.15    # env: B9_FRESHNESS_FLOOR
ENABLED         = env("B9_FRESHNESS_ENABLED") != "false"

def decay_multiplier(event, now=None):
    if not ENABLED:
        return 1.0
    published = parse_dt(event.get("published_at"))
    if published is None:
        return 1.0          # ← 解析失败给 1.0，不惩罚（数据问题不该让内容背锅）
    hours = max(0.0, (now or now_local() - published).total_seconds() / 3600)
    return max(MIN_MULTIPLIER, 2 ** (-hours / HALFLIFE_HOURS))
```

衰减曲线：

| 距今 | 0h | 12h | 24h | 48h | 72h | 120h |
|---|---|---|---|---|---|---|
| 倍率 | 1.00 | 0.84 | 0.71 | 0.50 | 0.35 | 0.18 |

---

## 4. 三个参数为什么是这个值

| 参数 | 值 | 理由 |
|---|---|---|
| **半衰期** | 48h（不是 24h） | 24h 下，2 天前的内容只剩 0.25 倍——对"昨天的大事今天还在发酵"这种常见情况**过于粗暴**，会把仍在持续影响市场的重大事件直接打没。48h 下：当天基本不打折、昨天打七折（够重要仍能留在前排）、2–3 天前显著沉底但不归零 |
| **地板** | 0.15（不是 0） | 归零 = "从排序里删除"，那是**展示窗口**该做的决定，不该由衰减曲线偷偷代劳 |
| **解析失败** | 返回 1.0 | 时间解析失败是**我们的数据问题**，不该让内容白白背锅沉底 |

> 衰减曲线要和展示窗口配套。当前展示硬闸 5 天，120h 时倍率 0.18 —— 曲线正好覆盖整个可见区间。

---

## 5. 存量字段怎么办

`score_timeliness` **保留不动**，但它不再承担排序里的时效职责。
它记录的是"我们抓到它时它有多新"，对**排查抓取延迟**仍然有用。

> ⚠️ 这意味着 `BaseScore` 里的 T 因子（16% 权重）与查询时的 freshness 倍率**是两件事**，
> 不要在实现时把它们合并。T 是入库时快照（用于诊断），freshness 是实时倍率（用于排序）。

---

## 6. 为什么不做定期重算

靠 cron 定期重算存量，只是把"过时"的粒度从**永远**缩小到**一个周期**，
而且每次重算都要全库写一遍。放在查询时算，**任何时刻取出来都是当下正确的值**。

同族的三个查询时倍率（市场重要性 / 新鲜度 / 情绪加成）遵循同一条原则：
**凡是依赖"现在几点""今天什么行情"的量，一律不落库。**

## 7. 验收断言

- [ ] 同一条事件，隔 48 小时再查，倍率减半（不是不变）
- [ ] `published_at` 为 null 的事件倍率 = 1.0，不沉底
- [ ] 5 天前的内容倍率 ≥ 0.15，不为 0
- [ ] `B9_FRESHNESS_ENABLED=false` 时全部返回 1.0
- [ ] **实验室与生产两条路径都接了这个倍率**（这一条曾经漏过：当天先加进了生产排序、实验室漏了，结果同一套权重在两个界面算出不同排名，生产首屏是当天内容、实验室把 2 天前的旧闻排在前面）
- [ ] 上线后 Top20 中 `published_at` 距今 > 3 天的条数 = 0
