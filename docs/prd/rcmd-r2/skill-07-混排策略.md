# Skill 06 · 混排策略（mix）

> **一句话**：加分项是**连续倾向**，保证不了「每 10 条必有 N 条」这种**结构性版面要求**——
> 分数分布一变，比例就变。混排管的是版面结构，不是分数。

---

## 1. 为什么加分项解决不了这个问题

老板要的是「打开就看得到能买的东西」。

如果只靠调高 `k_tradable`：

- 加分是**连续的**：0.06 的加成能不能把某条实体内容推进 Top10，取决于它和周围条目的分差
- 分差每一轮都在变（新内容进来、情绪变了、时效衰减了）
- 结果是**今天 Top10 有 6 条实体、明天只有 2 条**，而没有任何配置改动

> 加分项调的是**倾向**，混排定的是**结构**。两者不能互相替代。
> 而且**加分项的可解释性更好**：分数分布一变比例就变，但"被掉上来的那条自己会标注原因"，
> 所以"为什么这条在这里"始终可解释。**整池没有实体内容时不硬凑。**

---

## 2. 两个开关

### 2.1 实体配额 `min_tradable_per_10`（0–10，默认 0）

> 每 10 条稿件中，至少有 X 条是实体内容。

```python
window = 10
for start in range(0, len(out), window):
    end = min(start + window, len(out))
    if end - start < window:
        break                       # ← 不足一窗不强求，否则尾部会被反复搬运
    idx     = list(range(start, end))
    have    = [i for i in idx if has_tradable(out[i])]
    need    = quota - len(have)
    if need <= 0:
        continue
    # 候选：窗口之后、尚未使用的实体条目，按分数（即当前顺序）从高到低
    donors  = [j for j in range(end, len(out)) if has_tradable(out[j])]
    # 被换下的：窗口内非实体条目里分最低的（从窗口末尾往前）
    victims = [i for i in reversed(idx) if not has_tradable(out[i])]
    for _ in range(min(need, len(donors), len(victims))):
        j, i = donors.pop(0), victims.pop(0)
        out[i], out[j] = out[j], out[i]
        out[i][0]["mix_reason"] = f"配额提升（每{window}条保底{quota}条实体）"
```

**设计要点**：
- 借上来的是**后面分最高**的实体条目；换下去的是**窗口内分最低**的非实体条目 → **代价最小**
- 用**交换**（swap）：被换下去的条目落到原捐赠者的位置，不影响其它条目

### 2.2 置顶实体 `pin_tradable_top`（bool，默认 false）

> 开启后，Top1 和 Top3 位置强制是有实体内容。

```python
for pos in (0, 2):                  # Top1 与 Top3（0-based）
    if pos >= len(out) or has_tradable(out[pos]):
        continue
    donor = next((j for j in range(pos+1, len(out)) if has_tradable(out[j])), None)
    if donor is None:
        break                       # ← 整池都没有实体内容，不硬凑
    entry = out.pop(donor)
    out.insert(pos, entry)          # 用插入而不是交换：被顶下去的条目整体后移
    entry[0]["mix_reason"] = f"置顶实体（强制 Top{pos+1}）"
```

**为什么置顶用插入而不是交换**：Top1/Top3 是最高价值位置，
用交换会把一条低分内容直接扔到原捐赠者的位置（可能是第 15 位），
而**插入只是让被顶下去的整体后移一位**——对整体秩序的扰动最小。

### 2.3 叠加顺序

**先配额，后置顶。** 置顶是更强的约束，放在后面才不会被配额打乱。

---

## 3. 三条硬规则

| 规则 | 为什么 |
|---|---|
| **每次搬运必须写 `mix_reason`** | 被搬上来的条目**必须能解释自己为什么在这里**，否则"为什么这条在这"就变成不可解释的黑箱。实验室和线上卡片都要能显示它 |
| **整池没有实体内容时不硬凑** | 宁可不满足配额，也不能把无关内容伪装成交易机会 |
| **不足一窗（尾部 < 10 条）不强求** | 否则尾部会被反复搬运，每次翻页看到的顺序都不一样 |

---

## 4. 🔴 必须放在与生产共用的排序函数**内部**

混排如果写成"API 层拿到排好的列表再重排一遍"，
就会出现**实验室调的和线上跑的不是同一套**——这是我们在新鲜度衰减上已经犯过一次的错。

**正确做法**：把 `apply_mix_strategy` 放在 `rank_pool` 的最后一步，
生产与实验室都调 `rank_pool`，**由构造保证一致**，而不是靠两边各自记得同步。

---

## 5. ⚠️ 参数名单不允许手写第二份

我们真的出过：`k_tradable` 滑杆**完全是死的**——调到 0 和调到 0.20 排序**完全一样**。
根因是请求解析那一层有一份**手写的参数白名单**没有加这个键，在入口就被过滤掉了。

**根治办法**：所有参数名单从配置的 `DEFAULTS` 渲染出来，任何地方都不允许手写第二份。

```python
def resolve_mix_cfg(raw):
    out = dict(strategy_config.DEFAULTS["mix"])     # ← 名单来自单一事实源
    ...
```

> 同族的坑在这个项目里踩了**五次**：
> **取数 SQL / 计算 / 请求解析 / 响应序列化 / 界面渲染 是五个独立环节，漏哪一处都不报错。**
> 加一个参数必须五处一起改，并写一条端到端断言把它钉住。

## 6. 验收断言

- [ ] 配额从 0 调到 6，Top10 实体条数确实从 N 变成 **≥ 6**
- [ ] 置顶开启后，**Top1 与 Top3 必为实体条目**
- [ ] 每一条被搬运的条目都带 `mix_reason`，且实验室与线上卡片都显示得出来
- [ ] 整池 0 条实体内容时，不报错、不硬凑、顺序不变
- [ ] 尾部不足 10 条时不做搬运
- [ ] 配额 + 置顶同时开启时，**先配额后置顶**（置顶结果不被配额覆盖）
- [ ] `min_tradable_per_10 = 0` 且 `pin_tradable_top = false` 时，输出与混排前**逐条 id 一致**
- [ ] **实验室与生产 Top20 逐条 id 相同**（同一组参数下）
