| | |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-07-27 |
| 状态 | Demo 验证通过，交付正式研发 |
| 参考实现 | `crawler/pipeline.py`（LLM 结构化）/ `crawler/dedup.py`（聚类去重）/ `crawler/storage.py`（跨轮归并）/ `crawler/verification.py`（真实性校验） |
| 范围 | 输入是 PRD-01 产出的原始条目，输出是"结构化、去重、验证过的事件"。**五因子重要性打分与排序公式不在本期范围**，由另一份 PRD 承接；但 LLM 理解阶段产出的三个原始分量分（市场影响/权威度/内容质量）在本期范围内——它们是"理解"的产物，只是最终怎么加权排序不归这里管 |

---

## 一、目标

把 PRD-01 抓来的原始条目，变成**唯一、可信、带结构化标签**的"事件"：
1. 同一件事无论被多少家媒体报道、多少个 KOL 转发，最终只对应**一个事件 ID**；
2. 这个事件 ID 一旦生成，**跨天、跨轮次持续复用**，新证据是"更新"这个 ID 而不是"新建一行"；
3. 每个事件带有可信度判定——不是"LLM 觉得像真的"，而是有客观证据支撑的判定。

---

## 二、处理流程总览

```
PRD-01 原始条目
    ↓
① LLM 结构化理解 —— 每条原始条目 → 一个结构化"事件候选"
    ↓
② 语义聚合去重 —— 同一轮内，多个候选合并成一个事件
    ↓
③ 跨轮归并（核心："同一事件持续 update"的规则见第五节）
    ↓
④ 真实性校验 —— 客观信号打验证状态，不调用 LLM
    ↓
落库 / 更新
```

---

## 三、Step 1：LLM 结构化理解

**输入**：PRD-01 的一条原始条目（标题 + 正文/摘要 + 信源元信息）。
**输出**：一个结构化对象，字段如下（这是 LLM 一次调用的完整输出 schema）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `title_en` / `title_zh` | string | 双语标题，改写为可独立理解的一句话 |
| `description_short_en` / `description_short_zh` | string | 短摘要，含具体数字 |
| `description_long_zh` | string | 长摘要，**只产中文**（英文长文无下游消费方，纯增成本）。长度按事件重要性分档：越重要的事件摘要越长，具体分档规则由理解阶段自行定义并在实现中说明，不是本 PRD 的强制值 |
| `sector_tags` | array of `{sector, relevance, anchor}` | 板块标签，每个标签必须带相关度数值和判定依据（原文里支撑这个标签的具体文本锚点），不是简单打个板块名了事——这是"真相关才打标签"的量化落地 |
| `coins` | array of string | 涉及币种 |
| `entities` | array of `{name, type}` | 结构化实体，`type` ∈ `person/organization/project/chain/region/product`，比 `coins` 更丰富，供实体聚合与"同一主体历史新闻"召回用 |
| `sentiment` | enum `bullish/bearish/neutral` | 对市场的方向性影响，**不是**文章语气 |
| `sentiment_score` | float -1~1 | 数值化情绪，符号需与 `sentiment` 一致 |
| `impact_horizon` | enum `immediate/short_term/medium_term/long_term` | 影响时间尺度 |
| `news_type` | enum `market/policy/security/project/macro/other` | 新闻类型 |
| `event_tier` | enum `S/A/B/C/D` | 事件重要性档位（S=极重大·改变主要资产定价逻辑，依次递减），**这是分档，不是最终排序分**——最终排序公式在别的 PRD 里 |
| `event_subject` / `event_action` / `event_date` | string | **事件指纹三元组，是去重的第一道网**，见第四节。`event_subject`/`event_action` 要求是规范化 slug（如 `us_spot_btc_eth_etf` / `net_outflow`），不是自然语言句子 |
| `score_market_impact` / `score_authority` / `score_quality` | float 0~1 | 三个原始分量分，供排序公式消费；本 PRD 只要求产出，不规定怎么加权 |
| `credibility_score` | float 0~1 | LLM 主观可信度判断——**这只是参考信号之一**，最终验证结论由 Step 4 的客观信号主导，不能单独依赖这个字段 |
| `is_rumor` / `rumor_reason` | bool / string | LLM 判断是否传闻及理由 |

> **关键提醒**：`credibility_score` / `is_rumor` 是 LLM 的**主观**判断，历史上证明"写得像真的假新闻"能骗过它。真正的可信度判定要靠 Step 4 的客观信号（谁说的、几家独立机构说的、有没有人说反话、时间对不对得上），Step 1 这两个字段只作为最终判定的一个弱先验，不能单独作为结论。

## 四、Step 2：语义聚合去重（同一轮内）

**问题**：同一轮抓取里，多个信源可能报道同一件事（措辞不同），需要合并成一个事件。

**方法**（两层网，缺一不可）：

1. **稳定指纹**：用 `event_subject|event_action|event_date` 三元组算 `sha256(...)前16位`，作为事件的**唯一 ID**（不是拿 LLM 改写后的标题做 hash——标题每次改写措辞不同会导致 ID 不稳定，这是本项目实测踩过的坑）。指纹相同的候选，直接判定为同一事件。
2. **语义聚类兜底**：三元组没抽出来、或者措辞差异导致指纹没对上的，用**embedding 余弦相似度**兜底判同：
   - 模型：`text-embedding-3-small`，降到 **256 维**（1536 维默认精度用不上，且存储成本是 256 维的 6 倍）
   - **相似度阈值：0.82**（这是本项目实测标定出来的数字，**不是**教科书/文档里常见的 0.65——0.65 在实测中会把明显不同的两件事误判成同一件，请勿直接抄网上默认值，上线前务必用真实数据重新标定一遍）
   - 时间窗口：两条候选的事件时间差必须 ≤ 48 小时才允许合并，防止"同一主体、不同时间发生的两件事"被误判成一件（比如同一家交易所两次不同的安全事故）

同一簇内的多个候选合并为一个事件后：
- 信源列表取**并集**（不是只保留一条）
- 已合并的候选各自的信源明细（url、名称、发布时间等）都要保留，供第五节和 PRD 之外的排序模块使用

## 五、Step 3：跨轮归并 ——「同一事件持续更新」的规则（重点）

这一节直接对应产品侧的真实问题：**"同一个事件，不同的进展，其实应该归在一个事件的热度里"**，以及随后的确认："**会的。就是事件 id 不变，但是标签的值是会变化的**"、"**增量表那种逻辑。记录一个快照时间**"。请按下面的规则实现，不要按"每轮独立生成新事件"的思路做。

### 5.1 核心规则

同一件事在后续轮次里可能会有新进展（新增信源报道、互动量上涨、更多细节被披露），处理逻辑是：

1. **每轮开始处理前，先查库**：用第四节的稳定指纹 + embedding 相似度，去比对**近 72 小时内**已入库的事件（这个回溯窗口比语义聚类的 48 小时窗口略宽，是因为跨轮之间事件时间本身可能有度量误差，卡太紧会漏掉边界情况）。
2. **命中已有事件 → 更新，不新建**：事件的**主键（ID）不变**，几个字段的处理方式分两类：

| 字段类别 | 处理方式 | 举例 |
|---|---|---|
| **核心内容字段**：标题、摘要、事件发生时间 | **首次入库后不再覆盖** | 同一事件每轮被 LLM 重新改写，措辞会有细微差异，如果每次都覆盖，前端已经展示给用户的卡片文案会无故抖动。首次入库的版本视为"权威版本"，后续轮次即使 LLM 又生成了一版新措辞，也不写回 |
| **持续变化的"热度类"字段**：信源列表、信源数量、独立信源数、互动量、验证状态 | **每轮刷新/合并** | 信源列表取历史 ∪ 本轮的并集；互动量取历史和本轮两者中的较大值（防止某次抓取互动数据缺失导致数值倒退）；验证状态每轮用最新的完整信源列表重新计算 |
| **时间戳字段** | 两个都要留，含义不同 | `created_at`：这个事件 ID **第一次**被创建的时间，永久不变；`updated_at`：**这一轮**触发更新的时间，即"快照时间"，每次命中更新都要刷新 |

3. **判定"是不是同一事件"的比对基准**，要包含事件本身携带的完整信源明细（不只是信源名称列表），因为历史上出现过"信源名称列表"和"信源详细信息列表"两处字段不同步、导致下游把多信源报道的事件误判成孤证的问题——**这两处数据必须保持一致**，不能各自维护、各自更新。

### 5.2 增量式落库的实现建议

行为上等价于"增量表"：
- 主键 = 事件指纹（稳定、跨轮不变）
- 每轮处理时，对每条待写入事件先判断"库里有没有这个指纹/有没有语义相似的近期事件"
- 命中 → 执行 UPDATE（只更新第 5.1 节里"持续变化"那一类字段 + `updated_at`）
- 未命中 → 执行 INSERT（`created_at` = `updated_at` = 本轮时间）
- **不允许**对同一件事"先删再插"式地重建整行，否则 `created_at` 会被错误刷新，且如果外部系统（比如别的表用外键关联了这个事件 ID）会跟着断链

## 六、Step 4：真实性校验（客观信号，不调用 LLM）

**目的**：判断一个事件是否可信，靠的是客观证据而不是 LLM 的主观感觉。全部用代码计算，**零增量 LLM 成本**，复用 Step 2 已经算好的 embedding。

### 6.1 五个信号

| 信号 | 说明 |
|---|---|
| **多源交叉验证** | 有几家**独立机构**报道了同一事件——这是最强证据。「独立」按机构去重，不是按信源名字去重（同一机构的多个出口，比如某媒体的快讯号和文章号和 X 账号，只算一个独立源，需要维护一张机构别名表） |
| **信源可信度分层** | 官方一手 > 国际头部通讯社/头部加密媒体 > 有编辑部的加密媒体 > 聚合站/转载站/UGC > 陌生长尾账号，五档，每档有权重 |
| **单源孤证识别** | 只有一个低可信度来源时，不予验证，无视 LLM 主观判断觉得它"像真的" |
| **矛盾检测** | 库里已有语义相似但结论相反的事件（比如"传出被盗"和"官方辟谣未发生此事"），标记为存在争议 |
| **时间一致性** | 发布时间是否在未来、是否陈年旧闻冒充快讯、事件发生日期与发布日期是否对得上 |

### 6.2 转发折叠（2026-07-27 新增，必须实现）

**背景**：产品侧同事在评审时提出的真实问题——"**如果多个 KOL 单纯转发一个内容，算独立多个信源吗？**"，产品明确答复："**不算，只算非转载内容**"。

**要求**：在计算"独立机构数"时，同一事件下如果多个不同账号/机构的信源，其**正文内容**（复用 PRD-01 里的归一化比对逻辑）本质是同一段原文的转发/复制，**只保留其中权威分最高的一家**计入独立机构数，其余的记为"转发折叠"，不重复计数、不参与独立信源的可信度加成。

判定优先级（供实现参考）：
1. X API 结构化转推标记（若 PRD-01 已排除原生转推，这里主要处理引用推文 quote 和文本转发 text_repost）
2. 正文归一化后完全一致或高度相似
3. 命中转发折叠的信源仍然要保留在事件的信源明细里（不是丢弃这条数据），只是不计入"独立机构数"这个统计口径

### 6.3 判定结论

四档：`VERIFIED`（多家独立可信机构交叉证实，或官方一手信源）/ `PROBABLE`（单一可信来源，无矛盾）/ `UNVERIFIED`（孤证且来源可信度低）/ `DISPUTED`（检测到矛盾）。

## 七、完整输出字段规范

> 以下字段是本 PRD（Step 1-4）范围内需要产出并落库的全部字段，**不含**任何最终排序/重要性合成分（`importance_score` 等属于另一份排序 PRD）。

### 7.1 内容与理解字段

`id`（= 事件指纹）、`title_en`、`title_zh`、`date`、`time_event`、`time_get_data`、`description_short_en`、`description_short_zh`、`description_long_zh`、`sectors`（对外展示用，从 `sector_tags` 按相关度阈值过滤生成）、`coins`、`news_type`、`event_tier`、`entities`、`sentiment`、`sentiment_score`、`impact_horizon`

### 7.2 去重与归并字段

`event_subject`、`event_action`、`event_fingerprint`、`embedding`（256 维向量）、`sources`（完整信源明细，含 url/权威分/发布时间）、`source_names`（信源名称列表，**必须与 `sources` 保持同步**）、`source_count`、`merged_sources_count`

### 7.3 真实性校验字段

`verification_status`、`verification_score`、`verification_reason`（人工可读依据）、`verification_flags`（异常码列表，如 `REPOST_FOLDED`）、`independent_source_count`、`credible_source_count`、`is_rumor`、`rumor_reason`、`credibility_score`

### 7.4 时间戳字段（对应第五节的更新规则）

`created_at`（首次创建，永不变）、`updated_at`（最近一次更新的快照时间，每轮命中更新都刷新）

### 7.5 理解阶段产出、供排序消费的原始分量（本 PRD 只负责产出）

`score_market_impact`、`score_authority`、`score_quality`

## 八、验收标准

1. 同一事件跨天连续出现 3 轮以上，落库后**始终是同一个事件 ID、同一行记录**，不会变成 3 条独立记录；`created_at` 从第一轮起保持不变，`updated_at` 每轮刷新。
2. 标题/摘要类字段在多轮更新后**不发生无故改写**（前端展示文案不抖动）。
3. `sources` 与 `source_names` 两个字段任何时候长度/内容对应一致，不出现历史上"59 行数据两者长度不同导致误判孤证"的问题。
4. 构造"5 个不同账号转发同一段原文"的测试用例，`independent_source_count` 应判定为 1（而不是 5），`verification_flags` 里应出现转发折叠的标记。
5. 语义聚类阈值（余弦相似度）上线前必须用真实数据抽样标定，不能直接沿用某个默认值；标定结论需要写进实现文档留痕。
6. 真实性校验全程**零 LLM 调用**，只用规则代码和已有的 embedding 计算。
