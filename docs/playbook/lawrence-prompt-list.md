# Lawrence 常用 Prompt List

> 从历史全部对话中提取、去重、聚合、优化而来。
> **优化原则**：把你事后才补的约束前置进去——凡是你说过第二遍的话，都说明第一遍的
> prompt 漏了它，代价是一轮返工。下面每条都标了「防的是哪次事故」。
>
> 用法：复制代码块直接粘贴，`<>` 里的替换成当次内容。

---

## A. 开工

### A1 · 新任务启动（万能开头）

```
<任务描述>

标准约束（每次都适用，不用我重复）：
- 先讲清你打算怎么做，再动手；有多个方案就给推荐，别让我做选择题
- 独立的活并行做
- 缺数据就说缺，绝不填默认值糊过去
- 报任何数字前先对齐口径：这个数是怎么算的、代表什么、样本范围是什么
- 做完在真实界面上自己验一遍，别只看返回码
- 过程中的判断和踩的坑随手记进 TODO 和长期记忆
```

> **防的是**：`never-default-missing-data`（无日期当成"现在"，2024 年新闻顶着今天日期上前端）、
> `verify-metric-matches-claim`（把"SQL 取到 400 行"当成"缓存可用 400 条"）、
> `definition-of-done-user-surface`（落表≠交付）。

### A2 · 先规划再做（大改动/碰线上）

```
<需求描述>

先出方案再动手，不要直接改代码。方案里要有：
1. 现状是什么、问题在哪（基于你实际读过的代码，不是猜的）
2. 打算怎么改，为什么这么改
3. 会碰到哪些存量代码，有没有可能把线上搞崩
4. 怎么验证改对了、怎么回滚

绝对不要把线上搞崩。我确认方案后你再开工。
```

> **防的是**：策略实验室加 tab 那次的教训——大改动直接上手会漏掉存量影响面。
> 配合 `/engineering:architecture` 效果更好。

### A3 · 放手干（不想被打断时）

```
都做，不要再问我了，一路干下去。
遇到只有我能决定的事（会花钱、会通知到别人、不可逆）再停下来问，
其他的你自己判断，做完一起汇报。
```

> **注意**：这条会关掉我的确认习惯。**危险动作我仍会停**——删数据、发消息给同事、
> 花钱的操作。想连这些都放开，得单独说。

### A4 · 接手别人的（或自己三个月前的）代码

```
<要改的东西>

先别动手。按这个顺序摸清楚再说：
1. 这块代码的入口在哪、被谁调用、有几个消费面（主站/实验室/API/定时任务/导出，逐个列出来）
2. 它现在真实的行为是什么 —— 跑一遍看输出，不要只读代码猜
3. 哪些地方是"看起来没用其实有人依赖"的
4. 我要改的这一处，会波及上面哪几个面

列完清单再问我动不动手。
```

> **防的是**：`feature-must-cover-all-surfaces`（主站做了 tag 但实验室没有）、
> `lab-prod-must-share-formula`（实验工具和生产不同公式）。

### A5 · 多个 agent 并行分活

```
<要并行的活>

分活规则：
- 只有真正独立、不会改同一批文件的活才并行；有依赖的老实串行
- 每个 agent 的产出要能单独验证，别让我最后拿到一堆无法分辨谁写的东西
- **文件写出来不等于那个 agent 完成了**：以任务完成通知为准，
  不要看到文件存在就当它写完了，中途写入态会骗人
- 并行度别开太大，SSH 连接槽位是有限的，refused 不等于机器宕了

做完汇总时告诉我：哪几个成了、哪几个没成、没成的卡在哪。
```

> **防的是**：`agent-file-exists-not-agent-done`（把中途写入态当终稿发出去，整节缺失）、
> `parallel-agents-ssh-limit`（并行打爆连接槽位，refused 被误判成宕机）。

## B. 救火

### B1 · 服务异常（现象描述式）

```
<现象，例如：首页不更新了 / 情绪打分没有了 / 服务挂了>

先诊断再动手：
- 从"最近还有没有真的产出"这个终点往回查，不要只看组件活没活着
- 找到根因再修，不要凭现象猜
- 修完回补断档期间的数据
- 告诉我这次的根因是什么、以后怎么防
```

> **防的是**：`scheduled-job-never-ran`（组件级检查全绿、日志零 ERROR，产品已经三天没更新）。
> 端到端健康判据就是这次的产物。

### B2 · 修完要复盘

```
把这次事故记录下来，后面不要再犯。
要写清楚：现象是什么、根因是什么、为什么之前的检查没发现、以后靠什么防住。
记进长期记忆，不是写篇文档就完事。
```

> **防的是**：同类事故复发。停摆事故发生过两次，第二次才根治。

---

### B3 · 定时任务好像没跑

```
<哪个任务 / 本该什么时候跑>

别看配置对不对，先证明它到底跑没跑过：
1. 找出最近一次**真正执行**的痕迹（日志行、产出文件的 mtime、库里的写入时间）
2. 分清这三种：没到点、到点了但没触发、触发了但失败
   —— 注意"按设计延后"和"下游死了"在日志里长得一样
3. 检查执行环境的权限：跑它的那个身份能不能读到它要读的路径
   （软链、桌面目录、受保护目录都可能永远 EPERM）

结论要给证据，不要给"配置看起来是对的"。
```

> **防的是**：`scheduled-job-never-ran`（launchd 读不了 ~/Desktop，软链永远 EPERM，
> 而"按设计延后"与"下游死了"的日志长得一样）。

### B4 · 数据到底写进去没有

```
<哪张表 / 哪次写入>

不要拿返回码当证据。按这个查：
1. 直接查库：条数、最近一条的时间戳、关键字段有没有真的落值
2. 对比"应该写多少"和"实际写了多少"，差额要能解释
3. 检查是不是静默失败：占位符数量、字段数对不对，
   有没有只打了 warning 就返回 0 的路径

写入类的活，没有查过库就不算做完。
```

> **防的是**：`verify-write-not-just-return-code`（占位符少一个导致全部写入静默失败，
> 只打 warning 返回 0，差点当成"没新数据"）。

## C. 交付验收

### C1 · 上线前自检（最该常用的一条）

```
上线前自己走一遍：
- 列出所有会用到这个功能的角色，每个角色的完整旅程走通一次
- 只用界面上真实存在的东西操作，不要用你知道但用户看不到的路径
- 每个新加的控件真的点一次，看有没有产生预期的副作用
- 首屏肉眼扫一遍，可疑的数字搜一下

自检通过再告诉我"可以了"。
```

> **防的是**：`walk-each-role-journey-before-ship`（机制测试 13 项全绿，仍漏了"审批人看不到
> 申请内容"）、`control-shipped-but-never-fired`（控件绑了监听但从未触发过）、
> `human-eyeball-test-is-my-floor`（一天被抓三次）。

### C2 · 要完整数据（说一次就够）

```
把 <数据> 完整给我，我要拿去评测。

完整的意思是：
- 所有 ID、标题、字段值一律原样输出，不截断、不省略、不加省略号
- 行数不够就分批给，不要用"等 N 条"糊弄
- 同时给一份 CSV，我要能直接拖进表格
```

> **防的是**：我曾输出 8 字符 eventId、48 字符标题的"数据"，你追问了三次。
> 截断的评测数据等于没有。

### C3 · 给老板看的材料

```
<主题> 整理成给老板看的材料。

要求：
- 结论先行，第一段就说清楚"发生了什么/该做什么"
- 数字都要有出处，标明口径和样本范围
- 局限和没做到的地方如实写，不要粉饰
- 配图/流程图能说清的就别用大段文字
```

> **防的是**：汇报材料堆细节没结论。你要求过"方便我老板看"。

---

### C4 · 按角色走完整旅程

```
<这次改了什么>

上线前，把所有角色列出来（提交人 / 审批人 / 管理员 / 只读访客 / 第一次来的新人……），
然后**只用屏幕上真实存在的东西**，把每个角色的完整旅程走一遍。

不许用后台数据、不许用你知道的 URL 直接跳，就照普通人的点法走。
每条旅程告诉我：走通了 / 卡在哪一步 / 卡住时屏幕上显示的是什么。
```

> **防的是**：`walk-each-role-journey-before-ship`（机制测试 13 项全绿，
> 仍然漏了"审批人看不到申请内容"）。

### C5 · 前端控件是真的能用吗

```
<这次加/改的控件>

逐个触发一遍，看**真实副作用**，不是看它有没有渲染出来：
- 点下去有没有真的发生该发生的事（网络请求发了吗、状态变了吗、数据落了吗）
- 初始化时序：控件先出现、监听后挂上的那一段时间点它会怎样
- 有没有只靠颜色表达状态（色盲和强光下等于没状态）
- 全局变量兜底的那条路，在真实页面上还成立吗

三种失效都是静默的，所以必须逐个点，不能只看代码。
```

> **防的是**：`control-shipped-but-never-fired`（window.X 兜底 / init 时序 /
> 只用颜色表状态，三种失效全静默）。

### C6 · 报覆盖率的同时必须报首屏

```
<要报的指标>

聚合数字会掩盖首屏。报任何覆盖率/命中率时，同时给我：
- 整体数字
- **Top 10（用户真正看得见的那一屏）的实际命中**
- 两者差得远的话，解释为什么

"整体覆盖 90%、首屏 0/10"这种情况必须自己先说出来，别等我发现。
```

> **防的是**：`aggregate-number-hides-first-screen`（报"美股涨 18 倍"而首屏 0/10 有标签）。

## D. 数据与取数（Spade）

### D1 · 找表

```
帮我找 <用途> 的表。

选表标准（别再给我边缘表）：
- Asset Level 认 P0/P1，收藏数高的优先
- 必须有中英文描述，`bnb_dwd`/`bnb_dws`/`bnb_dwm` 标准层
- 不碰 `_ha` 后缀、`bnb_temp`/`bnb_dtest`/`ods`/`_bak_日期`
- 先去「数据专辑」(Data Map → DW Data) 按 板块→数据域→产品线 找，别盲搜关键词

定下来之前必须做两件事：
1. `SELECT MAX(分区)` 验数据真的在更新——元数据的"最近更新时间"是假的
2. 看字段清单，确认能回答我的问题（别拿累计口径的表来答单日问题）
```

> **防的是**：`fact_main_spot_order_d` 元数据写 2026-05 更新、实测数据停在 2021-04-17；
> `dws_main_trade_spot_order_uid_td` 全是 `_td` 累计口径没有 symbol。两次都是看了字段/
> 验了分区才发现。Kevin 和 Maya 都纠正过我的选表。

### D2 · 申请权限

```
把上面这些表的权限申请了。

- Read Only，时长选最长的（1 year / Permanent，别用默认的 7 days）
- 申请理由用这段：
  Apply for data to build a price alert sensitivity model to optimize the smart
  tooltips strategy in B9 project. As the senior strategy PM and data scientist of
  B9 recommendation. I will need user journey history, asset price change log, user
  features especially the marketing and transaction related ones, and other key
  dataset to build the model.
  后面补上这张表具体要哪几个字段、用来干什么。
- 提交完去 Access Center → My Request 核对真的在列表里，别看有没有弹提示
```

> **防的是**：提交成功的 toast 会一闪而过，我曾差点把"没看到提示"当成失败。
> 默认 7 天对建模项目完全不够。

### D3 · 跑数分析

```
用 tools/spade/spq.sh 查 <问题>。

- 必须带 date_key 分区过滤，神策表每天 170~210 亿条，裸扫会炸
- 时间比较用 TIMESTAMP '2026-08-18 12:00:00' 字面量，不能直接给字符串
- 拿到结果先自检：这个数合理吗？跟我的问题口径对得上吗？
- 数字反常就先怀疑自己的 SQL，别急着当成发现报给我
```

> **防的是**：`aggregate-number-hides-first-screen`（390 万条事件看着很足，拆开
> pageView 只有 77 个用户）。大数字最容易骗人。

### D4 · 批量回填

```
<要回填什么 / 范围>

回填前先过这三关，过不了就先停下来问我：
1. **语义污染**："最近 N 条"这类口径在回填时含义会变，会把历史数据算进当下
2. **饿死新数据**：同优先级 FIFO 会让回填任务把新数据挤到永远排不上
3. **成本旁路**：回填量大，确认走的是省钱那条链路，不是逐条打贵接口

给我预估：条数、耗时、花多少钱。我点头再开始。
```

> **防的是**：`backfill-three-traps`。

### D5 · 全库改写（三护栏）

```
<要改什么>

这是不可逆操作，四条护栏一条都不能省：
1. **默认预演**：先跑 dry-run，把将要改的行数和样例差异给我看
2. **写前快照**：备份表要和主表同 collation、同结构（加过列的话尤其）
3. **差异门**：改动比例超过阈值就自动停，等我确认
4. **互斥锁**：同一时间只允许一个改写任务

回滚验证不要信 UPDATE 的 rowcount，直接查库对数。
```

> **防的是**：`mass-rewrite-guardrails`（restore 别信 rowcount、备份表 collation 要对齐）。

### D6 · 改表结构 / 加列

```
<要加/改的字段>

加列会打破按 * 复制的脚本。改之前先 grep 全库：
- `SELECT *` 的地方（备份脚本、purge 脚本最容易中招，且总在"要删数据"那步炸）
- INSERT 时按位置而不是按列名的地方
- 备份表 / 影子表 / 实验表，是不是也要跟着加

列出全部受影响的地方，再动手。
```

> **防的是**：`schema-drift-breaks-star-select`。

### D7 · 改了公式/权重

```
<改了什么公式>

改完必查存量一致性：
1. 库里有多少数据是用旧公式算的？占比多少？
2. 不重算的话，效果对比是假的 —— 明确告诉我要不要重算、重算要多久
3. grep 全部排序/打分路径，确认没有第二处还在用旧公式
   （实验室和生产必须同公式、同取数轴）
4. 加一条 QA 断言把一致性钉住，别靠人记
```

> **防的是**：`verify-formula-version-consistency`（87% 的分是旧公式）、
> `lab-prod-must-share-formula`。

## E. 沉淀与归档

### E1 · 记经验

```
把这次的经验记进长期记忆，后面不要再犯。
写清楚：踩的是什么坑、为什么会踩、以后靠什么防住。
凡是人一看/一搜就能发现的问题，你都不该让它流到我这里。
```

### E2 · 归档备份

```
把 <范围> 全部整理进 GitHub 备份，以防丢失。
readme 好好写，要能让接手的人看懂这是什么、从哪读起。
密钥一律不进库，单独存我本机。
```

> **注意**：仓库是 public。归档时我会跑密钥扫描 + pre-commit 闸双层拦截。
> 曾漏过 `-p'密码'` 这种 shell 参数形式的明文密码，靠闸门拦下的。

---

### E3 · 从这次对话里提经验

```
把我们这次做的事提炼成经验，按这个格式，一条一个文件：

- **标题**：一句话说清是什么坑
- **现象**：当时看到的是什么
- **根因**：真正的原因（不是表面原因）
- **以后靠什么防住**：具体到某个检查动作/断言/清单项，不要写"要小心"
- **代价**：这次花了多少时间/钱/返工

只提**会再犯**的，一次性的意外不用记。
写完告诉我哪几条应该升级成常驻约束（每次都带上的那种）。
```

> **防的是**：`task-tracking-discipline`（定期做 memory 提取）。

### F3 · 这事该用规则还是该用模型

```
<要判断的东西>

先别急着加词表。回答我：
1. 现在的规则/正则漏的是哪几类？给具体例子
2. 这几类是不是结构性的（长距离分句、开放式短语、跨语言歧义）——
   如果是，加词表堵不住，加到第三轮就该停手
3. 换成 LLM 语义字段的话：成本多少、延迟多少、怎么评测准确率
4. 给个混合方案：规则做粗筛省钱，模型做终判

用实测数据说话，别用直觉。
```

> **防的是**：`keyword-blocklist-unreliable`（一天漏三次）、
> `punch-regex-structural-ceiling`、`semantic-judgment-needs-llm-not-rules`
> （规则误判 60%，LLM 12/12）。

## G. 成本

### G1 · 这条链路要花多少钱

```
<哪条链路>

按调用点逐个拆：
- 每个付费点：单价、频次、单次用量，算出日成本和月成本
- 哪几个点占了 80% 的钱
- 有没有能换成公司网关 / 本地算 / 缓存掉的
- 计费模型确认清楚：是按次、按 token、还是按条数 —— 搞错过一次就烧穿额度

给我一张表，按花钱多少排序。
```

> **防的是**：`b9-x-api-capacity`（误判计费模型两天烧穿额度 402 停摆）、
> `prefer-company-api-for-heavy-compute`。

### G2 · 加一个成本总开关

```
<要控制的成本>

先收敛闸口，再谈开关：
1. 列出全部付费点，散在几个文件里
2. 收敛成**单一入口**——付费点散在四处就不可能加总开关
3. 开关要 fail-closed：出问题时默认不花钱，不是默认花
4. 要能自动失效（比如超预算自动关），别只靠人记得关
5. **"跳过"和"故意丢弃"必须分开记账**，否则事后分不清是省了还是漏了
```

> **防的是**：`cost-gate-needs-single-chokepoint`（9 个付费点散在 4 处）。

## H. 写东西

### H1 · 写需求 / PRD

```
<要做的东西>

按这个结构写，每节都要能被人反驳：
1. **要解决谁的什么问题** —— 具体到角色和场景，不要写"提升体验"
2. **现在他怎么办的** —— 没有这个功能时的替代路径，以及它到底哪儿疼
3. **成了是什么样** —— 可验证的判据，不是"更好用"
4. **不做什么** —— 明确划出边界，防止评审时被无限扩
5. **怎么验证** —— 上线后看哪个数，多久看一次，什么算失败

写完自己挑三个最可能被挑战的点，先给出回答。
```

### H2 · 周报 / 进展同步

```
<这周做了什么（可以只给流水账）>

改写成给上级看的进展，规矩：
- 结论先行，一条一段
- 每条说清：**做完了什么**（可验证的状态，不是"推进了"）
- 卡住的单独列，写清卡在谁那里、我需要什么
- 数字必须带口径
- **局限和没做到的地方如实写，不要粉饰**

不要写"基本完成""正在推进"这类没有信息量的词。
```

### H3 · 把一堆材料变成给客户看的一页纸

```
<把材料贴在下面>

输出一页纸，结构：
1. **一句话结论**（如果对方只看一行，就看这行）
2. 三条支撑，每条一段，各自带证据和出处
3. **还没搞清楚的**：如实列，标明为什么没搞清楚
4. 建议的下一步，按性价比排序

要求：不许出现没有出处的数字；能给区间就不给点估计；
每个数字后面标注是[实测][公开来源][估算]中的哪一种。
```

### H4 · 帮我挑刺

```
<我的方案 / 我写的东西>

你的任务不是夸我，是把它拆了。给我：
1. 三个最致命的问题，按严重程度排序
2. 每个问题：为什么它致命、什么情况下会爆、怎么补
3. 我没想到但会被问到的三个问题
4. 如果你是唱反调的那个人，你会怎么反驳这个方案

不要先说优点。直接从问题开始。
```

## I. 通用

### I1 · 别顺着我说

```
接下来这段对话，请你：
- 我说错了直接指出来，不要先铺垫"这是个好问题"
- 不同意就说不同意，并给理由
- 我的前提有问题的话，先纠正前提，别顺着错前提往下答
- 不确定的地方明说"我不确定"，不要用流畅的语言掩盖

我要的是能反驳我的人，不是复述我的人。
```

> 对应 prompt pattern 里的 Reflection / 反奉承。日常最该常开的一条。

### I2 · 先问清楚再动手

```
<我的需求（可能说得不完整）>

动手之前，先列出你觉得**没说清楚、但会影响做法**的地方，
按"不问清楚会返工"的程度排序，最多五条。

每条给：你的默认假设是什么、如果假设错了会怎样。
我回答完你再开始。
```

> 对应 Question Refinement / Cognitive Verifier 模式。防的是照着半个需求做完再返工。

### I3 · 给我几个方案和取舍

```
<要决定的事>

给我 2–3 个真正不同的方案（不是同一个方案的三种措辞）。每个方案：
- 一句话说清它是什么
- 成本：时间 / 钱 / 复杂度
- 它牺牲了什么（一定有牺牲，写不出来说明没想清楚）
- 什么情况下它是错的选择

最后给你的推荐和理由。别让我做选择题，但要让我看得见你怎么选的。
```

### I4 · 检查你刚才那段

```
把你上面那段回答当成别人写的，挑错：
1. 哪些是**事实**、哪些是**推断**、哪些其实是**猜的**？逐句标
2. 哪些数字没有出处？
3. 哪些地方你其实不确定，但话说得很肯定？
4. 如果要推翻这段结论，最先该去查什么？

改完给我修订版。
```

> 对应 Fact Check List / Reflection 模式。贴回材料前跑一遍，能省掉一次返工。

### I5 · 解释给外行听

```
<要解释的东西>

讲给一个聪明但完全不懂这行的人听：
- 不用行话；非用不可的词，第一次出现时用一句话解释
- 先给一个生活里的类比，再讲真实机制
- 说清楚"如果这事没做好，会发生什么"
- 最后一句话总结

长度控制在他能一口气读完。
```
