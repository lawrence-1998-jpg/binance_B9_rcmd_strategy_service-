Lawrence 的 Prompt 库

从全部历史对话提取、去重、聚合而来。优化原则：把你事后才补的约束前置进去——凡是你说过第二遍的话，都说明第一遍漏了它，代价是一轮返工。

教训沉淀
A

开工

起手式，决定后面返工多少
A1

新任务启动 · 万能开头

任何新需求，把约束一次说清，省掉三轮来回

<任务描述>

标准约束（每次都适用，不用我重复）：
- 先讲清你打算怎么做，再动手；有多个方案就给推荐，别让我做选择题
- 独立的活并行做
- 缺数据就说缺，绝不填默认值糊过去
- 报任何数字前先对齐口径：这个数是怎么算的、代表什么、样本范围是什么
- 做完在真实界面上自己验一遍，别只看返回码
- 过程中的判断和踩的坑随手记进 TODO 和长期记忆
防的是无日期当成"现在"，2024 年新闻顶着今天日期上前端；把"SQL 取到 400 行"当成"缓存可用 400 条"报成果，实际可用 0 条。
A2

先规划再做

大改动、碰生产、动排序主链路时

<需求描述>

先出方案再动手，不要直接改代码。方案里要有：
1. 现状是什么、问题在哪（基于你实际读过的代码，不是猜的）
2. 打算怎么改，为什么这么改
3. 会碰到哪些存量代码，有没有可能把线上搞崩
4. 怎么验证改对了、怎么回滚

绝对不要把线上搞崩。我确认方案后你再开工。
配合使用加上 /engineering:architecture 会走完整的 ADR 流程，适合真正的架构决策。
A3

放手干

不想被反复打断、要连续产出时

都做，不要再问我了，一路干下去。
遇到只有我能决定的事（会花钱、会通知到别人、不可逆）再停下来问，
其他的你自己判断，做完一起汇报。
注意这条会关掉我的确认习惯。危险动作我仍会停——删数据、发消息给同事、花钱的操作。想连这些也放开得单独说。
B

救火

线上出问题时的两步
B1

服务异常

发现首页不更新、打分没了、服务挂了

<现象，例如：首页不更新了 / 情绪打分没有了 / 服务挂了>

先诊断再动手：
- 从"最近还有没有真的产出"这个终点往回查，不要只看组件活没活着
- 找到根因再修，不要凭现象猜
- 修完回补断档期间的数据
- 告诉我这次的根因是什么、以后怎么防
防的是组件级检查全绿、日志零 ERROR，产品却已经三天没更新。端到端健康判据就是这次事故的产物。
B2

修完复盘

紧接 B1 使用，别等事后补

把这次事故记录下来，后面不要再犯。
要写清楚：现象是什么、根因是什么、为什么之前的检查没发现、以后靠什么防住。
记进长期记忆，不是写篇文档就完事。
防的是同类事故复发。Mac 单点导致的停摆发生过两次，第二次才根治。
C

交付验收

最该常用的一组
C1

上线前自检

我说"做完了"之后、你验收之前

上线前自己走一遍：
- 列出所有会用到这个功能的角色，每个角色的完整旅程走通一次
- 只用界面上真实存在的东西操作，不要用你知道但用户看不到的路径
- 每个新加的控件真的点一次，看有没有产生预期的副作用
- 首屏肉眼扫一遍，可疑的数字搜一下

自检通过再告诉我"可以了"。
防的是机制测试 13 项全绿，仍漏了"审批人看不到申请内容"；控件绑了监听但从未触发过；一天被抓三次肉眼可见的问题。
C2

要完整数据

要拿数据去评测、比对、发给别人时

把 <数据> 完整给我，我要拿去评测。

完整的意思是：
- 所有 ID、标题、字段值一律原样输出，不截断、不省略、不加省略号
- 行数不够就分批给，不要用"等 N 条"糊弄
- 同时给一份 CSV，我要能直接拖进表格
防的是我曾输出 8 字符 eventId、48 字符标题的"数据"，你追问了三次。截断的评测数据等于没有。
C3

给老板看的材料

汇报、周报、对外说明

<主题> 整理成给老板看的材料。

要求：
- 结论先行，第一段就说清楚"发生了什么 / 该做什么"
- 数字都要有出处，标明口径和样本范围
- 局限和没做到的地方如实写，不要粉饰
- 配图 / 流程图能说清的就别用大段文字
经验你要求过"方便我老板看"。堆细节没结论的材料等于没写。
D

数据与取数

Spade 内网大数据平台
D1

找表

需要新数据源时，避免我给你边缘表

帮我找 <用途> 的表。

选表标准（别再给我边缘表）：
- Asset Level 认 P0/P1，收藏数高的优先
- 必须有中英文描述，bnb_dwd / bnb_dws / bnb_dwm 标准层
- 不碰 _ha 后缀、bnb_temp / bnb_dtest / ods / _bak_日期
- 先去「数据专辑」(Data Map → DW Data) 按 板块→数据域→产品线 找，别盲搜关键词

定下来之前必须做两件事：
1. SELECT MAX(分区) 验数据真的在更新——元数据的"最近更新时间"是假的
2. 看字段清单，确认能回答我的问题（别拿累计口径的表来答单日问题）
防的是fact_main_spot_order_d 元数据写 2026-05 更新、实测数据停在 2021-04-17；dws_main_trade_spot_order_uid_td 全是累计口径没有 symbol。Kevin 和 Maya 都纠正过我的选表。
D2

申请权限

表定下来之后

把上面这些表的权限申请了。

- Read Only，时长选最长的（1 year / Permanent，别用默认的 7 days）
- 申请理由用这段：
  Apply for data to build a price alert sensitivity model to optimize the smart
  tooltips strategy in B9 project. As the senior strategy PM and data scientist of
  B9 recommendation. I will need user journey history, asset price change log, user
  features especially the marketing and transaction related ones, and other key
  dataset to build the model.
  后面补上这张表具体要哪几个字段、用来干什么。
- 提交完去 Access Center → My Request 核对真的在列表里，别看有没有弹提示
防的是提交成功的提示一闪而过，我曾差点把"没看到提示"当成失败。默认 7 天对建模项目完全不够。
D3

跑数分析

有权限之后的日常取数

用 tools/spade/spq.sh 查 <问题>。

- 必须带 date_key 分区过滤，神策表每天 170~210 亿条，裸扫会炸
- 时间比较用 TIMESTAMP '2026-08-18 12:00:00' 字面量，不能直接给字符串
- 拿到结果先自检：这个数合理吗？跟我的问题口径对得上吗？
- 数字反常就先怀疑自己的 SQL，别急着当成发现报给我
防的是390 万条事件看着很足，拆开发现 pageView 只有 77 个用户。大数字最容易骗人。
E

沉淀与归档

防丢失、防复发
E1

记经验

任何一次"这个坑不该踩"之后

把这次的经验记进长期记忆，后面不要再犯。
写清楚：踩的是什么坑、为什么会踩、以后靠什么防住。
凡是人一看 / 一搜就能发现的问题，你都不该让它流到我这里。
已沉淀目前 49 条，在仓库 docs/memory/，带分主题导读。
E2

归档备份

阶段性收尾、怕丢失时

把 <范围> 全部整理进 GitHub 备份，以防丢失。
readme 好好写，要能让接手的人看懂这是什么、从哪读起。
密钥一律不进库，单独存我本机。
防的是仓库是 public。我曾漏过 -p'密码' 这种 shell 参数形式的明文密码，是 pre-commit 闸拦下的，不是我自己的扫描发现的。所以密钥扫描 + 提交闸两层都要在。
F

调研

要证据，不要我凭记忆编
F1

技术选型

评估外部 API、工具、供应商

调研 <问题>。

- 结论要有出处，给我能点开的链接或官方文档原文
- 分不清的地方明确说"不确定"，不要用听起来合理的话糊过去
- 涉及产品定位的（是 search API 还是聚合器？有没有这个字段？）必须去官方文档确认
- 最后给推荐，别只列清单
防的是我曾把 RavenPack 说成 search API，查了文档才发现 News Analytics 是 feed，只有 Bigdata.com 才是 search，且返回 chunk 不是全文。
F2

快速解释

遇到不认识的术语

<术语> 是什么意思？结合我们项目的场景说，别讲教科书定义。

没有匹配的 prompt，换个词试试。

不用每次重复
约定出处
