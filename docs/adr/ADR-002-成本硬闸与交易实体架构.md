# ADR-002：成本硬闸（Key 管理 + 零个人开销）与交易实体（新闻 agent → 事件 agent）

**状态**：Proposed（待 Lawrence 拍板后进开发）
**日期**：2026-08-02
**决策人**：Lawrence Zhu
**触发**：①个人 OpenAI 余额见底，要求"开关关闭时全链路一分钱不花"，公司 key 每 7 天轮换需要灵活替换能力；②老板反馈排序结果"刺激标的物交易的感觉不足"。

---

## 一、Context（现状实测，不是推测）

### 1.1 钱从哪儿花出去的——9 个付费点，没有闸口

全项目有 **4 处各自独立 `OpenAI(**kwargs)` 构造**、9 个实际付费调用点，没有任何统一入口：

| # | 位置 | 用途 | 现在谁付钱 | 桥覆盖 |
|---|---|---|---|---|
| 1 | `pipeline.py:801` | enrich 结构化（大头） | 命中缓存=公司；miss=**个人** | ✅ 仅 chat |
| 2 | `pipeline.py:1011` | semantic_prefilter（embedding） | **个人** | ❌ |
| 3 | `pipeline.py:1099` | aggregate_events 语义归并（embedding） | **个人** | ❌ |
| 4 | `sector_relevance.py:1026` | 板块相关性 | **个人** | ❌ |
| 5 | `scripts/rescore_factors.py:114` | 广度回填 | **个人** | ❌ |
| 6 | `scripts/backfill_dedup.py:82` | 去重回填 | **个人** | ❌ |
| 7 | `api/eval_tools.py:147` | 评测 Agent | **个人** | ❌（有 confirm_cost 闸） |
| 8 | `api/sector_insight.py` | 板块洞察 | **个人** | ❌ |
| 9 | `api/persona_tools.py:107` | persona 工具 | **个人** | ❌ |

这正是检修报告里"手写副本必腐化"（合并 B）的同族问题——**没有单一收费闸口，就没法做单一开关**。

### 1.2 关键实测发现（改变了方案形态）

**① 公司网关支持 embedding。** 今天实测 `POST /v1/embeddings` HTTP 200，模型 `text-embedding-3-small`、256 维——与 `crawler/dedup.py` 用的**完全一致**。此前架构假设"embedding 只能走个人 key"不成立。这意味着 #2/#3 两个付费点可以整体迁走。

**② 只逛 demo 网站是零成本的。** 前端实际调用的 21 个端点（`/api/news`、`/api/market-mood`、`/api/tools/reweight` 等）**全部是 MySQL 读取或纯计算**，不含任何 LLM 调用。所以"关成本时要不要停掉线上服务"——**不需要停**，站点该跑跑，它本来就不花钱。真正花钱的只有：入库流水线，以及评测/洞察这类用户显式触发的动作（#7/#8/#9）。

**③ 积压回补有 7 天硬天花板。** `fetch_staged_items(max_age_days=7)` 与 `/api/enrich/pending` 的 `fetched_at >= NOW() - INTERVAL 7 DAY` 两处都卡 7 天。**如果 key 断供或 Mac 离线超过 7 天，这批数据永久取不回来**——这是"自动回补"需求的最大结构性障碍，必须先拆掉。

**④ `consumed_at` 机制本身是对的。** 2026-07-26 已经把 fetch 与 mark 拆开（崩溃则原样重取）。回补能力的地基是现成的，不用重建。

### 1.3 时间上的冲突（必须先讲）

公司 key 按 WORKLOG 记录 **明天（08-03）到期**（今天实测仍活着，HTTP 200）。而本方案的默认状态是"关闭个人 key"。两件事叠加的直接后果：

> **key 一断且新 key 未到位 → 入库停摆，前端不再有新事件。**

这正是"即便停服也不要花钱"要的行为，不是 bug。但它必须**可见、可查、可自动恢复**，而不是静默停摆——否则就是检修报告里"静默失败家族"（合并 C）再犯一次。

## 二、Decision（方案总览）

分两块，**可以独立上线**，建议按 §五 的顺序。

```
┌─ 块 A：成本硬闸 ──────────────────────────────────────────────┐
│                                                               │
│   所有 LLM 调用 ──→ crawler/llm_gate.py（唯一闸口）           │
│                          │                                    │
│                    读开关 + key 注册表                        │
│                          │                                    │
│         ┌────────────────┴────────────────┐                   │
│      允许(公司)                       拒绝(个人,默认)          │
│         │                                 │                   │
│    Mac 走网关算                    不消费 staging              │
│    (chat + embedding)              记一笔 deferred            │
│         │                                 │                   │
│    写 llm_enrich_cache            留在队列等 key/开机          │
│         └────────────┬────────────────────┘                   │
│                  VM pipeline 只做"组装"，自己不调 LLM          │
└───────────────────────────────────────────────────────────────┘

┌─ 块 B：交易实体 ──────────────────────────────────────────────┐
│   三级取数阶梯（先免费后付费）：                               │
│   ① staging.matched_symbols 直通  ← Benzinga 98.1%/dxFeed 95% │
│   ② coins → binance_spot 校验     ← 加密侧，已有              │
│   ③ LLM 抽取                      ← 剩余长尾，要改 prompt     │
│              ↓                                                │
│   news_events.tradable_entities (JSON) → 标题后 tag + 加分项  │
└───────────────────────────────────────────────────────────────┘
```

## 三、块 A：成本硬闸

### 3.1 单一闸口 `crawler/llm_gate.py`

9 个付费点全部改为向它申请客户端，**没有第二条路**：

```python
# 唯一入口。拿不到就是拿不到，调用方必须处理 None
client = llm_gate.acquire(purpose="enrich", tier="chat")
if client is None:
    llm_gate.record_deferred(purpose="enrich", count=len(batch), reason=...)
    return []            # 不付费、不消费、留给下一轮
```

`acquire()` 的判定顺序：
1. 该用途是否被允许（`purpose` 白名单，见 3.4 的紧急模式）
2. 有没有可用的**公司**凭据 → 有则返回公司客户端
3. 开关是否打开 → 关（默认）则返回 `None`；开则返回个人客户端

**失败方向刻意选择 fail-closed**：DB 读不到开关、表不存在、任何异常 → 一律当"关闭"处理。成本闸的默认行为必须是不花钱，而不是"出错了就放行"。

### 3.2 Key 注册表（对应"灵活替换 key"）

秘密**留在 Mac 上**，不进 VM 数据库——理由不是安全加固（那是红线外的事），而是**VM 是挂着公网隧道的那一台，而公司 key 只有 Mac 用得上**（VM 连不通内网网关）。把只有 Mac 能用的秘密放进 VM，纯粹是白扩大暴露面，没有任何收益。

- **Mac 侧**：`~/.b9/credentials.json`（600 权限）存 key 列表，字段 `name / key / base_url / model / expires_at / added_at / status`
- **VM 侧**：只存**元数据**用于观测告警——`llm_credentials_meta` 表（`name / provider / expires_at / last_ok_at / consecutive_failures / status`），**永不存 key 本身**
- **轮换命令**（Mac 上一条命令，不改代码不重启）：

```bash
python3 scripts/b9key.py set --name company-0809 --key sk-xxxx --expires 2026-08-09
```

  该命令**先拿新 key 打一次真实网关调用**，通过了才落盘（fail fast，避免"填了个坏 key 却以为没事"），落盘后把旧 key 标 `expired`，并把元数据同步给 VM。

- **到期预警**：worker 每轮检查 `expires_at`，≤2 天时日志 WARNING + 写 VM 元数据表；tab07 监控看板出一张"key 剩余天数"卡（正好补上检修报告里 tab07 的 KPI 缺口之一）。

### 3.3 开关的存放与生效

- 落在 DB（`runtime_flags` 表，`key/value/updated_at/updated_by/expires_at`），**改了立刻生效、不用重启不用改代码**
- 环境变量 `B9_ALLOW_PERSONAL_KEY=1` 作为**紧急逃生门**（DB 挂了也能开）
- **默认关闭**；开启时**必须带自动失效时间**（默认 6 小时，最长 24 小时）

  自动失效这条是我加的，理由：需求原话是个人 key"只在紧急情况用"。紧急是有时限的，而人在救火时最容易忘记关回去——把"忘记关"这个最可能的失败模式从流程纪律变成机制保证。到点自动回到不花钱状态。

- **强制配套 QA 断言**（吃检修报告合并 A 的教训，杜绝又一个死配置）：
  - `runtime_flags` 每个键必须在消费方代码里有真实读取点
  - 开关关闭时跑一轮 pipeline，断言个人 key 调用次数 == 0

### 3.4 关闭状态下各付费点的行为

| 付费点 | 关闭时行为 | 影响 |
|---|---|---|
| enrich 结构化 | 只用缓存；miss 则**不消费 staging**，记 deferred | 新事件入库变慢/暂停，数据不丢 |
| aggregate_events embedding | 用 Mac 随 enrich 一起返回的向量（见 3.5） | 无影响 |
| semantic_prefilter embedding | **跳过**（保留字面预过滤） | 只影响省钱效率，而它省的本来就是不再发生的个人开销 |
| sector_relevance / 回填脚本 | 拒绝执行并明确报错 | 手动运维动作，报错即可 |
| eval / sector_insight / persona | 返回 4xx + 明确文案"成本闸已关闭" | 用户显式动作，给明确反馈而不是静默失败 |

**这里有一个必须讲清楚的取舍**：关闭状态下 VM 的 pipeline 从"生产者"退化为"组装工"——它只把 Mac 算好的缓存拼装入库，自己不产生任何 LLM 调用。好处是成本绝对可控；代价是**入库吞吐完全受制于 Mac 的在线时长**，而网关有 30 req/min 硬限（实际按 25 走）。按当前 staging 约 6000 条/天的增量，Mac 需要每天在线约 4 小时才能持平；断供多日后追赶一个 4 万条的积压，需要约 28 小时的 Mac 在线时间。**这个数字应该进监控，而不是等发现首页没新内容了才回头查。**

### 3.5 embedding 随 enrich 一起回传（省掉一个付费点）

既然网关支持 embedding，且 Mac 拿到条目后本来就要算 enrich，就让它**顺手把 `embedding_text()` 的向量一起算出来回传**：

- `/api/enrich/submit` 的每条 result 增加可选字段 `embedding`（256 维 float 数组）
- VM 侧存进现有的 `news_events.embedding` blob 列（列已存在，跨轮归并本来就在用）
- `aggregate_events` 优先用已有向量，只有缺失的才需要现算

单条 embedding 成本约为 enrich 的千分之一量级，顺带算几乎不增加网关压力，却**整体消灭了 #2/#3 两个付费点**。

### 3.6 积压回补（对应"自动回扫并回补"）

**先拆 7 天天花板**——这是最关键的一步，其余能力其实已经具备：

1. `fetch_staged_items` 与 `/api/enrich/pending` 的窗口改为配置项，默认 **30 天**
2. 超窗条目不再静默消失，而是转入 `status='cold'` 并计数展示（要恢复得显式决策，避免无声丢数据）
3. `raw_items_staging` 增加 `deferred_count` / `last_deferred_at` / `defer_reason`，"为什么还没处理"可查
4. **回补是自动的**：Mac worker 每 15 分钟唤醒、每批最多 1000 条、按 `priority ASC, fetched_at ASC` 取——新 key 到位或 Mac 开机后，它自然就开始排干积压，不需要额外的"回补脚本"
5. 新增 `GET /api/enrich/backlog` 与 tab07 卡片：积压条数、最老条目年龄、按天分布、预计排干时间

**对应需求的"停掉后能有记录或可查能力"**：staging 表本身就是账本（`consumed_at IS NULL` = 待办），补上 defer 原因和监控视图即可，不需要新建一套队列。

## 四、块 B：交易实体（新闻 agent → 事件 agent）

### 4.1 问题的真实根因（实测）

近 5 天全池 8359 条的标的物覆盖：

| market_scope | 条数 | 有标的物 | 覆盖率 |
|---|---|---|---|
| **us_stock** | **4163（50%）** | **32** | **0.8%** |
| crypto | 1210 | 642（其中币安可交易 579） | 53%（可交易 47.9%） |
| macro_policy | 650 | 8 | 1.2% |
| general | 1565 | 5 | 0.3% |
| 其它 | 771 | 6 | <1% |

**老板的"刺激标的物交易感觉不足"不是加分项缺失，是占池一半的美股内容根本没有标的物这个字段**——`coins` 按设计只抓加密 ticker（prompt 明写 `bitcoin→btc`）。全池整体覆盖率约 7.5%。

### 4.2 免费的大头：ticker 一直在被丢掉

`raw_items_staging.matched_symbols` 近 5 天实测：

| type | 条数 | 带真实 ticker | 占比 |
|---|---|---|---|
| **benzinga** | 6336 | **6217** | **98.1%** |
| **dxfeed** | 363 | **345** | **95.0%** |
| rss / web_search / scraper | 23751 | 7 | ~0% |

样本长这样：`Update: Equities Rise Intraday as Microsoft's Post...` → `DJI,IXIC,SPX,MSFT,AMZN,AAPL,META`

这些是 Benzinga 编辑部**自己标注**的 ticker（不是我们猜的），落进了 staging，**只被用来做优先级路由，从没进过 `news_events`**。接上这条通路：

- **零 LLM 成本、零 prompt 改动**（不动 prompt = 不触发缓存失效，这在 key 紧张期特别重要）
- 直接把美股侧覆盖率从 0.8% 拉到接近 Benzinga 的供给占比

### 4.3 数据模型

新增列 `news_events.tradable_entities` (JSON)：

```json
[{"symbol":"NVDA","market":"us_stock","venue":"NASDAQ","name":"NVIDIA",
  "tradable":true,"confidence":"high","source":"benzinga_ticker"},
 {"symbol":"BTC","market":"crypto","venue":"binance_spot","name":"Bitcoin",
  "tradable":true,"confidence":"high","source":"coin_metrics"}]
```

**"能买到"的判据**（这是需求的硬约束，必须可验证而不是拍脑袋）：

| 类别 | 判据 | 数据来源 |
|---|---|---|
| 加密 | `coin_metrics[].binance_spot == true` | 已有，走 data-api.binance.vision |
| 美股 | ticker ∈ 标的物全集白名单 | 新建静态表（S&P500 + Nasdaq100 + 加密概念股 + 已有 21 个 dxFeed 精选） |
| 指数/ETF | ∈ `DXFEED_INDEX_SYMBOLS`（SPY/QQQ/DIA/IWM…） | 已有 |
| 其它市场（日韩港） | **v1 不标**，`tradable:false` | 币安用户实际买不到，标了是噪音 |

白名单的意义：Benzinga 一条新闻最多挂 12 个 ticker，其中不少是边缘小盘股。**只展示用户真买得到、且认得出的标的**，避免首页变成 ticker 刷屏。

### 4.4 三级取数阶梯

```
① staging.matched_symbols 直通  → 覆盖 Benzinga/dxFeed，零成本零 prompt 改动
② coins → binance_spot 校验     → 覆盖加密，逻辑已存在
③ LLM 抽取 tradable_symbols     → 覆盖 RSS/web_search 长尾，需改 prompt
```

**③ 必须单独排期**：给 enrich schema 加字段会改变 `PROMPT_VERSION_HASH` → **整个 enrich 缓存全部失效** → 全部内容要用公司额度重算一遍。在 key 明天到期、7 天一轮换的当口做这件事，是拿唯一的算力通道去冒险。①② 已经能覆盖大部分内容且完全免费——**先上 ①②，③ 等新 key 到位、积压清空后再做**。

### 4.5 交易实体加成（新加分项）

```
FinalScore = BaseScore × MarketWeight × NewFresh
             × (1 + bonus_align + bonus_reversal + bonus_tradable)
```

`bonus_tradable` 建议初始值 **+0.06**，分档：

| 情况 | 加成 |
|---|---|
| 有可交易标的 + 单一主标的明确 | +0.06 |
| 有可交易标的但挂了 ≥5 个（宽泛市场评论） | +0.02 |
| 无可交易标的 | 0 |

分档的理由：`DJI,IXIC,SPX,SPY,QQQ,IWM,MSFT` 这种挂 7 个 ticker 的"盘前综述"恰恰是**最没有交易指向性**的内容，真正"刺激交易"的是"NVDA 财报炸了"这种单一主标的事件。不分档会让泛泛的大盘综述被系统性顶上去，与需求意图相反。

**三条必须遵守的既有教训**：
1. 进 `strategy_config` 的 `DEFAULTS` **且必须有真实消费点** + QA 断言（合并 A 的死配置教训）
2. 同时改 `crawler/scoring.py` **和** `api/lab_tools.py` 的 `rank_pool`，QA 平价断言必须仍 ≥9/10（lab-prod 同公式教训）
3. 纳入既有 `bonus.cap` 总上限，不能让三个加分项叠加突破封顶

### 4.6 前端展示

标题后跟 tag，样式区分可交易性与市场：

```
英伟达Q2财报超预期，盘后涨9%  [NVDA] [美股]
比特币ETF单日净流入创新高      [BTC·币安] [加密]
```

- 可交易的给强调色（赤陶）+ 点击可跳转（跳哪儿待定，见开放问题）
- 每条最多展示 3 个，超出折叠成 `+N`
- 复用现有 `.tag` 体系，不引入新组件

### 4.7 一个必须提示的策略风险

检修报告刚确认了两件事：首屏已经**60% 是美股**，且**冲击力因子(I，权重 23.5%)正在把税率/占比误读成涨跌幅**。现在再加"有标的物就加分"，三者叠加会把排序进一步推向"**带一个大数字的单只美股新闻**"——而那恰好是误读最集中的地方（美股 avg score_punch 0.384 vs 加密 0.255，财报误读集中在美股）。

建议：`bonus_tradable` **上线后立刻用策略实验室做一次 Top20 换手对比**，重点看加密占比是否被进一步挤压。如果挤压明显，优先级应该是先修同事件归并（合并 D）和 punch 语义字段，而不是回调这个加成——因为它本身是对的，问题在于它放大了别处的既有缺陷。

## 五、实施顺序（建议）

| 阶段 | 内容 | 工作量 | 为什么是这个顺序 |
|---|---|---|---|
| **A1** | `llm_gate` 单一闸口 + 开关（默认关）+ fail-closed + QA 断言 | M | key 明天到期，闸口必须先于到期日到位 |
| **A2** | Key 注册表 + `b9key.py` 轮换命令 + 到期预警 | S | 配合 7 天轮换节奏 |
| **A3** | 拆 7 天天花板 → 30 天 + defer 账本 + backlog 端点/看板 | M | 断供期间数据不丢的前提 |
| **A4** | embedding 随 enrich 回传，消灭 #2/#3 付费点 | S | 让"零个人开销"真正闭环 |
| **B1** | matched_symbols 直通 + binance_spot 校验 + 落库 + 前端 tag | M | **零成本零 prompt 改动**，先拿走大头 |
| **B2** | `bonus_tradable` 加分项 + 实验室对比验证 | S | 依赖 B1 的数据 |
| **B3** | LLM 抽取长尾标的物（改 prompt） | M | **必须等新 key 到位、积压清空后**再做 |

A1–A3 是"明天 key 到期前应该到位"的部分。

## 六、Consequences

**变容易**
- 成本从"事后看账单"变成"事前硬闸"，且默认安全（fail-closed）
- key 轮换从改代码/重启变成一条命令，且带真实调用校验
- 断供不再等于丢数据；恢复后自动排干，不需要人工触发
- 美股内容第一次有了标的物，"事件 agent"的定位有了数据支撑

**变难**
- 关闭状态下入库吞吐**完全受制于 Mac 在线时长**（约需 4 小时/天持平）
- 9 个付费点全部要改造成"拿不到客户端也能优雅退化"，改动面不小
- 多了一层闸口，排查"为什么没数据"时要先看开关和 key 状态（所以监控必须同步做，否则就是新的静默失败源）

**需要复查**
- `bonus_tradable` 上线后的首屏市场构成（会不会进一步挤压加密占比）
- 30 天窗口对 staging 表体积的影响（当前约 6000 条/天 → 30 天约 18 万行，需确认索引与磁盘）
- 白名单式的美股标的物全集需要定期维护（又一个"手写表会腐化"的候选，建议一开始就从可更新的数据源生成而不是手写死）

## 七、裁决（Lawrence，2026-08-02）

1. **"紧急情况"放行范围** → **只放行重大事件**。个人 key 打开时不是全量恢复，低价值内容继续留队列等公司 key。

   **实现上的一个修正**：`event_tier`（S/A/B/C/D）是 LLM **产出**的字段，在"要不要花钱处理这条"的决策点上还不存在——不能用它做闸。改用 `raw_items_staging.priority`（0=权威大盘 / 1=大盘指数 / 2=加密头部 / 3=长尾 / 4=个股），它在入库时就算好了，正是为"哪些内容值得优先处理"设计的。默认放行 **P0–P2**。

   **成本估算修正**：ADR 初稿写"约为全量的 15%"是拍的，实测 5 天 staging 分布为 P0 **23.4%** / P1 0.3% / P2 4.6% / P3 64.8% / P4 7.0%——**P0–P2 实际占 28.3%**（P0 偏高是因为 Benzinga 量最大且被归在权威大盘档）。按全量 $100–130/天 估，紧急模式约 **$28–37/天**。

   因此追加**第二道兜底**：`emergency_daily_item_cap`（默认 2000 条/天）。开关的 6 小时自动失效管的是"忘记关"，日配额管的是"开着的这几小时里量突然暴涨"，两道闸方向不同、都要有。
2. **美股标的物范围** → **大盘蓝筹白名单**（S&P500 + Nasdaq100 + 加密概念股，约 600 支）。用户认得出、买得到；小盘股新闻不标 tag，接受覆盖率损失换首页干净。
3. **tag 点击行为** → **v1 纯展示不可点**。先验证"有标的物"本身是否提升了交易感，跳转后续再加。
4. **停摆的对外表达**（未单独裁决，按默认执行）：前端不加中断提示条，安静展示存量事件；状态在 tab07 监控看板可查。理由：给外部使用方看到"系统坏了"的信号，代价高于收益，而运维需要的可见性由看板承担。
